The umbrella owns the `vendo` bin. It has nine commands.

## `vendo init [dir]`

Non-interactive setup with zero questions on the happy path. It scans the app,
scaffolds the server surface (an empty `vendo/registry.tsx` plus the
composition wired to it), writes the `.vendo/` contract, and — on Next.js —
generates the `vendo/vendo-root.tsx` client mount, which renders
`<VendoOverlay />`, the visible launcher + panel. Theme is extracted
automatically and auth is detected from `package.json`. See
[vendo init](/connect/vendo-init) for the full walkthrough and
[the agent playbook](/agents) for the agent-driven flow.

**Init never writes to a file you authored.** Every file it creates is new and
Vendo-owned; the only exception is `package.json`, where it maintains its own
`predev`/`prebuild` hooks. Mounting `<VendoRoot>` in your layout is therefore
yours to paste, and init ends with a framed block naming the exact file and
lines:

```
────────────────────────────────────────────────────────────────
ONE STEP LEFT — paste this yourself (init never edits your files)

  File: app/layout.tsx
    import { VendoRoot } from "../vendo/vendo-root";
    … then wrap: <VendoRoot>{children}</VendoRoot>

  vendo/vendo-root.tsx mounts <VendoOverlay />, the visible launcher +
  panel — until this lands, Vendo is wired but invisible.
  Then confirm it landed: npx vendo doctor
────────────────────────────────────────────────────────────────
```

The same step rides `--agent` as a `mount` object (`{ file, lines, why }`) and
as the first entries of `manualSteps`. Until it lands, `vendo doctor` fails
with [E-WIRE-004](/agents/verify#E-WIRE-004) and prints the same paste.

Init detects the host framework from `package.json`: a `next` dependency
scaffolds `app/api/vendo/[...vendo]/route.ts` (under `src/app` when that
directory exists); an `express` dependency scaffolds `vendo/server.ts`
(`vendo/server.mjs` without a `tsconfig.json`) holding the `createVendo()`
composition and a Node HTTP-to-fetch adapter, plus a starter registry. Mount
the adapter with `app.use("/api/vendo", mountVendo())` and wrap the client
entry in `<VendoRoot>` to finish. See [vendo init](/connect/vendo-init) for
detection precedence and the non-interactive `--framework` fallback.

`dir` is the app to initialize and defaults to the current directory.

Init also adds idempotent `predev`/`prebuild` `vendo sync` hooks to
`package.json` and writes critical-tool risk answers to `.vendo/overrides.json`,
which future sync runs respect.

Options:

- `--agent` emits the setup plan as JSON and writes nothing: the detected
  framework, every file init would write, every proposed code diff (all
  Vendo-owned files), `mount` (the `<VendoRoot>` paste as
  `{ file, lines, why }`) plus the same lines in `manualSteps`, `extraction`
  (deterministic extraction runs first,
  against a throwaway directory, so the plan carries the extracted tools),
  and `riskRecommendations` (per-tool advice: destructive tools should be
  marked critical, disabled tools reviewed before enabling). It is a read-only
  plan, not a scaffolding step; scaffold with `--yes`.
- `--yes` skips the interactive prompts (auth confirm, theme review, Cloud
  offer) and scaffolds non-interactively, ending with an `Agent tail:` block
  naming the files left to hand-edit.
- `--auth <preset>` wires an auth preset without asking: `authJs`, `clerk`,
  `supabase`, `auth0`, `jwt`, or `none`.
- `--framework <next|express>` overrides detection; required non-interactively
  when detection fails.
- `--cloud-key <key>` writes an existing Vendo Cloud key to `.env.local`;
  `--byo` declines the Cloud offer (bring your own model key).
- `--ai` / `--no-ai` force the AI pass on or off — tool judgment
  (descriptions, risk, brief) and theme-slot filling, one consent for both.
  Without either flag, an interactive run **asks, every run** (nothing is ever
  saved) and a non-interactive one skips. `--yes` counts as non-interactive.
  `--ai-polish` is the older spelling of `--ai` and still works. The same
  rule and the same flag pair apply to `vendo sync`.
- `--engine <claude|codex|npx>` pins which engine runs the AI pass instead of
  first-available (`claude` = Claude Agent SDK or the `claude` CLI, `codex` =
  the `codex` CLI, `npx` = the npx-fetched engine on Vendo Cloud fuel). A
  pinned engine that is not available skips the AI pass with one loud line —
  it never falls back to a different provider. Interactively, when more than
  one engine is available, the consent question itself becomes a pick (your
  source goes to the provider you choose), so the flag is mostly for
  unattended runs.
- `--theme <slot=value>` overrides a theme slot value directly (repeatable).
- `--force` regenerates Vendo-owned files under `.vendo/`. It does not replace
  existing host source files.

Init rejects options it does not recognize and exits 1 before doing anything.
This means a flag the installed CLI does not support (for example `--agent`
on an older version) can never be silently dropped and turn a read-only
request into a writing init.

When the host repo has a `.claude/` directory and no
`.claude/skills/vendo-setup/SKILL.md`, init also writes the `vendo-setup` agent
skill shipped inside the npm package. An edited copy is never overwritten;
deleting the copy makes init write it again on the next run, like any missing
scaffold.

The `predev` and `prebuild` hooks init adds keep extraction running alongside
your dev and build scripts:

```json
{
  "scripts": {
    "predev": "vendo sync --no-ai",
    "prebuild": "vendo sync --strict --no-ai"
  }
}
```

The hooks carry `--no-ai` explicitly, so a `npm run dev` or `npm run build`
can never stop to ask a question or spend on inference. If a script already
exists and does not call `vendo sync`, the command is prepended and existing
formatting is preserved. If it holds the hookless entry an older init wrote
(`vendo sync` / `vendo sync --strict`, exactly), re-running init upgrades that
one entry in place; any other `vendo sync …` in your scripts is your own call
and is left untouched.

## `vendo login [email]`

Claims a Vendo Cloud key through the [auth.md](https://vendo.run/auth.md)
user-claimed ceremony: the CLI opens a claim, shows the pairing code and
approval URL, and polls until the request is approved in the browser. The
minted `VENDO_API_KEY` is written to `.env.local` — never printed. The
success message may suggest re-running `vendo init`; that applies only to a
repo that is not wired yet. In an already-initialized repo nothing needs
re-running — the runtime picks the key up from `.env.local` on the next
turn, and `vendo doctor` confirms it.

In a terminal (TTY) the browser opens automatically at the approval URL; the
URL and code stay printed as the fallback. For a non-TTY caller — a coding
agent driving the CLI — nothing opens: the command prints the approval URL and
pairing code for the human to act on, exactly as before.

The pending claim is persisted to `~/.vendo/pending-claim.json` (mode 0600),
so if the polling process dies before the approval lands, a fresh `vendo
login` resumes the same claim — it prints "Resuming pending approval" with the
original code, and the approval still mints the key into the `.env.local` the
original run was aimed at. An expired pending claim is discarded and a fresh
one opened.

Options:

- `[email]` or `--email <address>` pre-fills the approval page (login hint).
- `--wait <seconds>` bounds how long this one invocation polls before giving
  up — capped by the claim's expiry. When the budget elapses with the request
  still pending, the command prints a resumable line, leaves the pending claim
  in place, and exits `0` (pending is not a failure). A re-run resumes the same
  claim. `--wait 0` opens (or resumes) the claim, polls once, and exits
  resumably if still pending — the "open and print the code" first call. Absent
  the flag, behavior is unchanged: it blocks until the claim expires (~10 min).
  Built for coding agents: run short bounded calls in a loop instead of one
  long blocking call that a command timeout would kill mid-wait (see
  [agents](/agents)).
- `--api-url <url>` overrides `VENDO_CLOUD_URL` (default
  `https://console.vendo.run`).

`vendo cloud device-login` is the same command (kept as an alias). The
email-OTP `vendo cloud login <email>` remains available as a fallback.

## `vendo doctor [dir]`

Checks wiring, makes one live `/status` round trip, GETs the app's root page
(a 5xx there fails doctor — a live wire with crashing pages is not a working
install), and sends one seeded message through the mounted `POST /threads`
route to prove the wired model answers. It recognizes both Next.js (catch-all
route plus any layout that mounts `<VendoRoot>`) and Express (the server
composes `createVendo` from `@vendoai/vendo/server`; the client mounts
`<VendoRoot>`), and it fails unless a VISIBLE surface is mounted somewhere —
`<VendoOverlay />`, `<VendoThread />`, a BYO embed, or a surface hook —
because `<VendoRoot>` alone renders nothing a user can reach. It ends with
the config line that unlocks each remaining block.

Doctor also runs two live HTTP probes against the running dev server so silent
credential-forwarding traps surface before you ship:

- **Present-mode forwarding.** Doctor calls `POST /doctor/present` and the
  composition executes a synthetic same-origin tool. The echo route reports
  booleans indicating whether the doctor's `authorization` and `cookie`
  headers reached the host API. The probe fails with actionable text when
  `VENDO_BASE_URL` is unset or points at the wrong origin, when the binding
  is cross-origin, or when the dev server is down. No credential values are
  printed, logged, or persisted.
- **actAs mint and verify.** Doctor calls `POST /doctor/act-as` so the
  host-configured `createVendo({ actAs })` mints auth material and the host's
  own principal resolver accepts it. This works with any `actAs`
  implementation, including the [actAs presets](/connect/act-as-presets).
  When `actAs` is unconfigured, doctor warns but does not fail; mint or
  verify errors produce actionable failure text.

The synthetic `/doctor/*` routes are development-only and return 404 in
production.

The live turn resolves its model through the same
[dev-mode credential ladder](/connect/dev-mode) the runtime uses, so doctor
and runtime agree on what is wired. Exit 0 means a real user would have
gotten an answer; the turn must produce a non-empty reply. When nothing is
listening on the dev port, an interactive run offers to start `npm run dev`
for the probe (`--yes` starts it non-interactively) and stops it afterward.

Doctor also checks that `VENDO_API_KEY` is present and well formed when set
and prints the "what Cloud unlocks" hint either way.

Options:

- `--url <url>`: override `VENDO_URL` for the probe target.
- `--yes`: start the dev server for the probe without asking.
- `--json`: print exactly one machine-readable object on stdout with
  `{ vendo, version, wired, exit, checks, liveTurn, cloud, summary }`
  and suppress every other line. `wired` is true when no static or HTTP
  check failed; `exit` reflects the process exit code, which additionally
  requires `liveTurn.ok`.

When the MCP door is open, doctor also validates the registry discovery surface:

- both OAuth metadata documents (`/.well-known/oauth-protected-resource/...`
  and `/.well-known/oauth-authorization-server/...`) resolve
- the server card at `/.well-known/mcp/server-card.json` parses
- a `server.json` in the project root, if present, matches the MCP registry
  schema and its remote URL agrees with the live door
- a local `public/.well-known/mcp-registry-auth` challenge file starts with
  `v=MCPv1`, and the same challenge served over HTTP parses when present

Exit codes:

- `0`: green (wiring, HTTP checks, and the live model turn all passed)
- `1`: broken wiring, a failed HTTP probe, or an unanswered live turn

See [Doctor error codes](/agents/verify) for the symptom, cause, and fix
behind every check.

## `vendo sync [dir]`

Runs the build-step scan manually. Sync owns the WHOLE scan: tool extraction,
remix baselines, the host component catalog, and the theme, for `dir`, which
defaults to the current directory. The default is fail-soft and warns on
breaking changes.
When tools changed or broke, sync asks the running dev server which saved
apps, automations, and grants they impact and prints one `impact:` line per
tool (or `impact unknown` when no server is reachable). Drifted pins get an
advisory `drifted:` line. Drift never auto-rebases; each fork's owner
decides.

Sync also scans host source for
[`<Remixable>` wrappers](/connect/host-components#remix-fork-a-wrapped-component)
and captures each wrapped component into `.vendo/remixable/<slot>.json`. A
wrapper it cannot capture — inline JSX, a child that is not statically
imported, an anonymous default export — is a hard `error:` line (one per
wrapper, with file, line, and fix) and the run exits 2 in any mode: the
single-importable-child constraint is defended loudly, never degraded
silently. On a run with no wrapper errors, baselines whose slot matches no
wrapper anymore are deleted with one `pruned:` line each. Capture also warns
(`warning:` lines, never failing) when an instant-kind wrapped component
reaches into host plumbing — router imports, context-style hooks,
function-typed props — and suggests `<Remixable review>`, since plumbing does
not cross the fork boundary.

Sync scans exported JSX components referenced by your `<VendoRoot>`
`components` map and writes `.vendo/catalog.json` (see
[Host components](/connect/host-components)). Rescans are deterministic and
byte-stable, so the file is safe to commit. Both `sync` and `init` print one
status line summarizing what was found:

```
catalog.json: 2 discovered, 2 registered
```

A malformed existing `.vendo/catalog.json` fails sync loudly instead of
being silently overwritten.

### The theme re-scan

Sync re-runs the same deterministic theme scan `vendo init` does and
reconciles it with `.vendo/theme.json`, so a rebrand actually reaches the
agent instead of it rendering last quarter's colors forever. Hand edits are
never clobbered.

Provenance rides a sibling merge base, `.vendo/theme.extracted.json` — what
the deterministic scan produced last time, written by init and kept current by
sync. It mirrors the split `.vendo/` already lives by (`tools.json` is the
machine layer, `overrides.json` is what a person decided), and it leaves
`theme.json` exactly the frozen `VendoTheme` shape. Commit both. Per slot:

A slot is machine-owned **only** when the base records it and `theme.json`
still holds exactly that value. Everything else is yours:

- recorded, and `theme.json` still equals it → machine-extracted; sync takes
  the new value
- recorded, and `theme.json` differs → you edited it; pinned, and reported
  with both values so the choice is visible
- **not recorded at all** — no base file yet, or a token init never saw →
  pinned. There is no evidence about who chose the value on disk, and Vendo
  will not guess from "it looks like one of our defaults" (the neutral
  defaults are ordinary Tailwind palette values — `#2563eb` is blue-600 — so
  guessing would silently overwrite a real brand choice).

Values are compared by meaning, not bytes: `#FFFFFF` and `#ffffff` are the
same color.

**Derived slots follow their source.** `accentText` is the accent's contrast
color, `headingFamily` inherits `fontFamily`, and `radius.small`/`radius.large`
scale from `radius.medium`. A derived slot moves only when its source moves —
so a pinned accent keeps its own contrast text rather than getting the one
computed for your app's accent (which is how a hand-picked dark blue would end
up with black text on it). `radius.small`/`radius.large` additionally hold if
you tuned them away from the derived values.

The summary line names exactly what happened, and only that: the "re-read"
list is the set of slots actually written to `theme.json`, and pinned slots are
reported separately with both values.

```
theme: 1 slot re-read from your app (accent) → .vendo/theme.json · 1 pinned by you, unchanged (border — yours #111111 vs your app's #e2e8f0) — `vendo sync --theme-refresh` takes your app's values
```

`--json` mirrors it as `theme: { updated, pinned }`, both lists of slot names.

The base only advances on an unambiguous run — one with no pinned slots. So an
install from before the base existed touches nothing and warns with the diff on
**every** sync until you either accept it with `--theme-refresh` (which takes
every changed slot and records the base) or edit `theme.json` yourself. When
the scan and `theme.json` already agree everywhere, the base bootstraps
silently. The file has no timestamp and is rewritten only when its values
change, so a no-op sync leaves your tree clean.

### Pin baselines reach Vendo Cloud

When a Vendo Cloud key resolves (`VENDO_API_KEY`, `.env.local`/`.env`, or
`--key`), a normal sync also reconciles the captured baselines in
`.vendo/remixable/` with the `vendo_pin_baselines` collection in your project's
hosted store — the collection the console's Remix reviews screen reads. New and
changed slots are uploaded, slots whose baseline **file is gone** are deleted
remotely, and one line reports both. This does **not** require `--report`.

A baseline file that exists but cannot be read (a truncated or half-written
capture) is skipped with a warning and its Cloud row is left alone — only an
absent file is a deletion signal, so a bad file on one machine can never wipe
the console's review baseline. The whole reconcile runs under one ~20s budget;
if it runs out, whatever already landed is still reported and the rest retries
on the next sync.

What crosses the wire is the baseline file verbatim: the wrapped component's
**source**, the source of every module it imports within the capture depth, and
the captured app-root stylesheets. That is the point — a reviewer cannot review
a fork's diff against source Cloud does not have — but it is worth knowing
before you set a key. Keyless and BYO installs make no request at all; the
baselines stay on disk. A Cloud failure is a warning line and never changes the
exit code; the next sync retries.

### The judgment pass

After the structural scan, sync judges the freshly extracted catalog: a coding
agent grades each tool with a verbatim source quote behind every proposal, an
independent skeptic checks each one, and the surviving judgments land in
`.vendo/judgments.json`. Candidates are chosen by drift — a changed `srcHash`
or a binding mismatch — unless `--full` judges everything. Hardenings and prose
apply themselves; loosenings wait for a human (`--review` asks now, otherwise
they queue as `pending`).

`.vendo/overrides.json` is **not** written by this pass. It is read-only prompt
context now, and it means exactly one thing: what a human decided. A re-sync
can never clobber either file.

Whether the pass runs at all follows the same rule as `vendo init`:

| | no flag | `--ai` | `--no-ai` |
| --- | --- | --- | --- |
| Interactive (TTY) | asks, **every run** | runs | skipped |
| Non-interactive | skipped, with a note | runs | skipped |

Nothing is ever persisted, so an interactive run asks again every time. A
non-interactive run with no flag stays deterministic and never spends —
which is why the hooks init installs pass `--no-ai` explicitly.

"Non-interactive" means CI, a pipe, `--json`, `--yes`, **or a run started by a
package script** (`predev`, `prebuild`, any `npm run …` — detected via
`npm_lifecycle_event`). A lifecycle hook inherits your terminal, so without
that last rule an older install's bare `predev: vendo sync` would stop
`npm run dev` on a prompt whose reflexive Enter starts spending. A run you did
not invoke never gets a question. Engines resolve
like init's ladder: a BYO model key (`ANTHROPIC_API_KEY` / `OPENAI_API_KEY`),
then `VENDO_API_KEY` managed inference, then none — keyless syncs stay
structural-only, and the pass never fails a run.

Options:

- `--strict`: CI gate: exit 2 on breaking tool changes, exit 3 when a
  breaking tool impacts saved references.
- `--json`: print exactly one machine-readable object on stdout:
  `{ ok, exitCode, report, impact, notes, theme, baselines }`, where `report`
  carries `tools`/`breaking`/`pins`/`remixableErrors`/`catalog`/`warnings`
  (`pins` lists the slots captured, drifted, and pruned this run), `impact`
  is the per-tool blast radius (`[]` when nothing changed, `null` when unknown),
  `theme` is `{ updated, pinned }` (or `null` with no `.vendo/theme.json`),
  `baselines` is `{ pushed, pruned }` (or `null` when keyless), and `notes`
  collects CLI-level events. An `error` field appears when extraction itself
  failed soft. `--json` never prompts.
- `--url <url>`: override `VENDO_URL` for the blast-radius impact query
  against a running dev server (`POST /sync/impact`).
- `--report`: push the report to Vendo Cloud (requires `VENDO_API_KEY` or
  `--key`; `--api-url` overrides `VENDO_CLOUD_URL`).
- `--review`: show the queued and new loosenings and confirm before writing
  (interactive; cannot combine with `--json`).
- `--full`: judge the whole catalog instead of only what moved.
- `--engine <name>`: pin the judgment engine family (`claude`, `codex`,
  `npx`); an unavailable pin skips loudly, never falls back.
- `--ai`: run the judgment pass with no prompt, interactive or not.
- `--no-ai`: force the judgment pass off (what the installed `predev`/
  `prebuild` hooks pass, so committed files never churn and a build never
  spends). `--no-watermark` remains accepted as an alias.
- `--yes`: this run cannot ask — take the flags as given and never prompt.
- `--theme-refresh`: take the theme scan's values even for slots you
  hand-edited.
- `--key <key>` / `--api-url <url>`: the Vendo Cloud key and console base URL
  used for the baseline reconcile (and `--report`).

```console
$ vendo sync --strict --no-ai --url http://127.0.0.1:3000/api/vendo
tools: +0 -0 ~1
pins: 1 captured, 0 drifted
pruned: LegacyHeroCard — stale baseline deleted (no <Remixable> wrapper names this slot anymore)
catalog.json: 2 discovered, 2 registered
theme: 2 slots re-read from your app (accent, accentText) → .vendo/theme.json
baselines → Vendo Cloud: 1 pushed, 1 pruned (component source crosses the wire so the console can review forks)
breaking: host_listAccounts input-narrowed
impact: host_listAccounts breaks 1 automation, 1 grant
```

The report names any remixable slots whose captured baseline changed and
points to rebase; user forks of those pins are now drifted and keep
rendering their previous content until an explicit rebase replays the
recorded edit trail onto the new baseline. See
[Host components](/connect/host-components#drift-and-rebase).

Exit codes:

- `0`: success — warnings (missed imports, plumbing hints, drift advisories)
  never fail the run
- `2`: `<Remixable>` wrappers that cannot be captured (any mode), or breaking
  tool changes when `--strict` is set
- `3`: breaking tool changes that impact saved apps, automations, or grants
  when `--strict` is set

## `vendo eject <surface> [dir]`

Copies a shipped chrome surface's presentation source out of the installed
`@vendoai/ui` into your repo as code you own, shadcn-style. Pixels are
copied; data and wire logic stay a package dependency. The templates'
package-internal imports are rewritten to the public `@vendoai/ui` subpaths,
so protocol updates keep flowing to ejected code. A `.vendo-eject.json`
manifest in the ejected directory records the surface and package version,
which doctor uses for its drift check.

Options:

- `--list`: print the ejectable surfaces (with `--list`, the first
  positional is the target dir).
- `--force`: overwrite an existing ejected directory.

## `vendo extract [dir]`

Applies a coding agent's extraction draft through the same deterministic
guards init's built-in pass uses. The flow: `vendo init --agent` emits the
read-only plan with the `aiPolish` delegation contract, an external agent
writes a draft from it, and `vendo extract --apply <draft.json>` parses the
draft, runs the deterministic guards, writes the same artifacts, re-syncs,
and prints the same summary. Non-interactive safe; exits non-zero on an
unusable draft.

Options:

- `--apply <draft.json>`: required. The draft file the agent produced.
- `--force`: regenerate Vendo-owned files.

## `vendo try`

Serves a live local demo of your product's agent before you install anything.
Run it from your app's repo: a deterministic read-only pass extracts your
tools and brand theme (host-authored `.vendo/` files such as `theme.json`,
`brief.md`, and `design-rules.md` are carried over and win), the demo opens
in the browser in seconds, and the AI pass then deepens the profile in the
background through the same engine ladder `vendo init` uses: product brief,
risk polish, use-case chips, and synthetic fixtures, streamed into the
surface as each stage lands. The first paint never waits on AI.

Zero commitment, guaranteed: nothing is written to your repo, no key is
required, and Ctrl+C leaves no trace. Every artifact lands in a temp profile
that is swept on exit.

Chat is live when a model credential resolves at startup: a provider env key
(`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, or `GOOGLE_GENERATIVE_AI_API_KEY`) or
`VENDO_API_KEY` through the Vendo Cloud model gateway, the same
[dev-mode credential ladder](/connect/dev-mode) the runtime uses. An
Anthropic or Vendo Cloud key works alone (Vendo ships `@ai-sdk/anthropic`);
a non-Anthropic key needs its matching `@ai-sdk/*` provider installed in
your app. With a
model resolved, the surface also takes corrections in conversation: refine
proposals arrive as reviewable diffs and apply to the temp profile only,
never to your repo. With zero keys, or outside a repo, everything still
serves against scripted data.

Options:

- `--port <port>`: listen on a fixed port (default: any free port).
- `--no-open`: print the URL without opening the browser.
- `--engine <claude|codex|npx>`: pin the deepening engine family instead of
  first-available. An unavailable pin skips deepening with one loud line; it
  never falls back to a different provider.
- `--no-ai`: skip background deepening entirely; the demo stays on the
  deterministic profile.

Liked it? `npx vendo init` installs the agent for keeps. See
[Try Vendo](/try) for the full walkthrough, including the hosted domain-paste
venue at [vendo.run/playground](https://vendo.run/playground).

`vendo playground` is retired: `vendo try` absorbed its job (the scripted
surfaces still serve when try runs keyless or outside a repo). Running the
old command prints an error pointing at `vendo try`.

`vendo refine` is retired too: `vendo sync`'s enrichment pass owns AI
curation of `.vendo/` (compounds and briefs live in `.vendo/overrides.json`
now), and the try surface's refine panel carries the conversational
correction loop. Running the old command prints an error pointing at
`vendo sync`.

## `vendo mcp`

Tooling for publishing your door to the official MCP registry. Both
subcommands operate on the current directory unless you pass a target `dir`.
See [Publish to the MCP registry](/capabilities/mcp-registry) for the full
walkthrough; flags below.

### `vendo mcp server-json`

Generate and validate the `server.json` artifact the registry expects. The
command reads your `package.json` for the name, version, description, and
homepage, then combines that identity with the domain namespace and public
door URL you pass in.

```bash
npx vendo mcp server-json --domain example.com --url https://app.example.com/api/vendo/mcp
```

Options:

- `--domain <domain>`: registry namespace to publish under. Prompted if omitted.
- `--url <public-mcp-url>`: public URL of the live door. Prompted if omitted.
- `--force`: overwrite an existing `server.json`.

On success, doctor's registry checks compare the file against the running
door on every run.

### `vendo mcp verify-domain`

Generate the Ed25519 keypair and challenge string you need to prove ownership
of a registry namespace. The private seed is written only to the path you
choose so you can keep it outside the repository.

```bash
npx vendo mcp verify-domain \
  --domain example.com \
  --key-out ~/.vendo/mcp-registry.key \
  --write-well-known ./public
```

Options:

- `--domain <domain>`: required. Registry domain you are proving.
- `--key-out <path>`: required. Path for the private key seed. Written with
  mode `0600` and refuses to overwrite an existing file.
- `--write-well-known <dir>`: optional. Also writes the challenge to
  `<dir>/.well-known/mcp-registry-auth` so your host can serve the HTTP
  proof.

The command prints both the DNS TXT record and the HTTP challenge value
(`v=MCPv1; k=ed25519; p=<base64>`). Publish either to satisfy registry
verification, then pass the private key's hex value to `mcp-publisher` when
authenticating.

## `vendo cloud`

Client for the Vendo Cloud API. `vendo cloud device-login` is the alias of
[`vendo login`](#vendo-login-email) — the headline way to get a key. The
email-OTP fallback `vendo cloud login <email>` sends a 6-10 digit code,
prompts for it, and stores the session at `~/.vendo/cloud-session.json`;
`--token <jwt>` stores an access token instead.
Other subcommands: `logout`, `whoami`, `orgs`, `keys` (`list`, `create`,
`revoke`), `members`, `invite`, and `usage`. Read
results print as JSON. There is no validate subcommand: key problems
surface on the first real call, and `vendo cloud usage` reads the
server-side metering from real traffic. Billing lives in the
[console](https://console.vendo.run) only.

There is no deploy subcommand. With `VENDO_API_KEY` set, automations you
build sync to Vendo Cloud automatically and run on Vendo's schedulers — see
[Vendo Cloud](/deploy/vendo-cloud) for the full walkthrough.

Global options:

- `--api-url <url>` overrides `VENDO_CLOUD_URL` (default `https://console.vendo.run`).

`members` and `invite` take `--org <id>`; `keys` and `usage` take
`--project <id>`. Either can be omitted when there is exactly one candidate —
one organization on the account, one project in the organization. Run
`vendo cloud help` for the full list. See
[Vendo Cloud](/deploy/vendo-cloud) for setup, keys, and sharing.

## Telemetry opt-out

Set `VENDO_TELEMETRY_DISABLED=1` or set `"optedOut": true` in
`~/.vendo/telemetry.json`. `DO_NOT_TRACK`, CI, and production runtime also
disable build and development telemetry.
