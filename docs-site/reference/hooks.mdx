`@vendoai/ui` exposes headless React hooks that read from the same wire the
built-in chrome uses. Pair them with your own UI when you need a bespoke
surface, or drop them next to `VendoOverlay` to power an inline widget.

Every hook on this page is exported from the package root:

```ts
import { useThreads, useApprovals, useVendoThread } from "@vendoai/ui";
```

## The shared read shape

The collection hooks all return the same read fields, so you can render
loading, error, and empty states with one pattern across the whole surface.
Each hook names its collection after what it holds — `threads`, `apps`,
`pending`, `grants`, `connections`, `automations`, `events`.

```ts
// The shape every collection hook spreads, shown for useThreads. The type
// itself is internal — name it through the hook
// (ReturnType<typeof useThreads>) rather than importing it.
{
  threads: ThreadSummary[];      // seeded, never undefined: [] before the first read lands
  error: Error | undefined;      // last fetch error, or undefined when the read succeeded
  isLoading: boolean;            // true only on the first load; refresh does not flip it
  refresh: () => Promise<void>;  // re-fetch on demand; resolves after the read settles
}
```

Two details matter when you write against it:

- **The collection is seeded, not `undefined`.** A collection hook starts at
  `[]`, so `threads.length === 0` means "empty *or* not loaded yet" — read
  `isLoading` to tell those apart. `useApp` is the exception: it returns a
  single document, so its `app` is `AppDocument | undefined`.
- **`error` is `undefined`, not `null`,** when the read succeeded. A failed
  read keeps the last good collection, so you can render a retry affordance
  without blanking the surface.

`isLoading` is `true` only for the first fetch. Subsequent `refresh()` calls
and background polls do not flip it back to `true`, so a spinner shown on
first mount does not flash on every update.

## Available hooks

| Hook | Returns | Polling |
| --- | --- | --- |
| `useThreads(options?)` | `threads`: `ThreadSummary[]`, plus `get(id)` and `remove(id)` | `pollMs` |
| `useApp(appId)` | `app`: `AppDocument \| undefined`, `surface`, plus `call(ref, args)`, `edit(instruction)`, `history` | — |
| `useApps(options?)` | `apps`: `AppDocument[]`, plus `create`, `remove`, `fork`, `exportApp`, `importApp` | `pollMs` |
| `useApprovals(options?)` | `pending`: `ApprovalRequest[]`, plus `decide(ids, decision, options?)` | `pollMs` |
| `useGrants(options?)` | `grants`: `PermissionGrant[]`, plus `revoke(id)` | `pollMs` |
| `useConnections(options?)` | `connections`: `ConnectionAccount[]`, plus `disconnect(id, connector?)` | `pollMs` |
| `useConnectorCatalog()` | `{ options, resolved, explicit, failed, retry }` — the connect dock's effective catalog | — |
| `useAutomations(options?)` | `automations`: `AutomationEntry[]`, plus `enable`, `disable`, `runs`, `dryRun`, `stopRun` | `pollMs` |
| `useActivity(options?)` | `events`: `AuditEvent[]`, plus `hasMore` and `loadMore()` | `pollMs` |
| `useSlotApp(slotId, options?)` | `{ appId, error, isLoading, refresh }` — the app currently placed in a slot | on by default |
| `useVendoStatus()` | `{ posture, connected }` | — |
| `useVendoThread(threadId?)` | the streaming conversation — see [Threads](#threads) | — |
| `useVendoOverlay(options?)` | `VendoOverlayController` — see [Overlay control](#overlay-control-usevendooverlay) | — |
| `useMobileTakeover()` | `{ active, keyboardInset, style }` — the full-bleed mobile breakpoint | — |
| `useApprovalSheetPresentation()` | `boolean` — whether an in-thread consent presents as the bottom sheet | — |

**There is no generic `execute` callback.** Hooks that write name their
verbs: `decide`, `revoke`, `disconnect`, `enable`, `disable`, `create`,
`remove`, `fork`, `importApp`, `edit`, `dryRun`, `stopRun`. Each returns a
promise, and the ones that change the collection refresh it when they
resolve. `exportApp` is the exception — it is a pure read and refreshes
nothing. Either way the hook's `isLoading` still tracks only the first read,
so drive mutation-pending UI from your own `await`.

## Polling

Pass `pollMs` to the hooks marked above to keep the value fresh without a
manual refresh. Polls are self-scheduling rather than interval-driven: the
next tick is armed only after the current refresh settles, so a slow server
never stacks overlapping requests.

```tsx
"use client";

import { useApprovals } from "@vendoai/ui";

export function ApprovalBadge() {
  const { pending, error, isLoading, refresh } = useApprovals({ pollMs: 5_000 });

  if (isLoading) return <span aria-hidden />;
  if (error) return <button onClick={refresh}>Retry</button>;

  return pending.length > 0 ? <span>{pending.length} to review</span> : null;
}
```

Omit `pollMs` for a one-shot fetch on mount. Polling does not pause when the
tab is hidden — a hidden tab keeps fetching on the cadence you set, so pick a
number you are willing to pay for in the background, or call `refresh()` from
your own trigger instead.

`useApp` and `useVendoStatus` take no options and never poll. `useApp` still
returns `refresh()`, so you can re-read it on demand; `useVendoStatus` returns
only `{ posture, connected }` — it reads once per mount, and remounting is the
only way to re-read it. `useSlotApp` is the
opposite: it polls every 5 seconds by default, because a placement made in
the conversation surface has to appear in the slot on its own. Pass
`{ pollMs }` to change the cadence, or `{ enabled: false }` to stand the
discovery down entirely.

## Threads

`useThreads` reads the same thread summaries `VendoOverlay` uses, so you can
build a custom conversation list without giving up parity with the shipped
chrome.

```tsx
"use client";

import { useThreads } from "@vendoai/ui";

export function ThreadList({ onSelect }: { onSelect: (id: string) => void }) {
  const { threads, error, isLoading, refresh } = useThreads();

  if (isLoading) return <p>Loading…</p>;
  if (error) return <button onClick={refresh}>Retry</button>;
  if (threads.length === 0) return <p>No conversations yet.</p>;

  return (
    <ul>
      {threads.map((thread) => (
        <li key={thread.id}>
          <button onClick={() => onSelect(thread.id)}>{thread.title}</button>
        </li>
      ))}
    </ul>
  );
}
```

`ThreadSummary.title` is always a string — no `?? "Untitled"` fallback
needed.

Pair with `useVendoThread(threadId)` to drive the streaming turn for the
selected conversation. It wraps the AI SDK's `useChat`, so its vocabulary is
the AI SDK's:

```ts
const {
  threadId,      // the effective id: yours, or the one the server minted on the first turn
  messages,      // UIMessage[]
  sendMessage,   // send a turn — NOT `send`
  status,        // the AI SDK chat status ("ready" | "submitted" | "streaming" | "error")
  error,
  approvals,     // the turn's pending approval parts, ready to render
  addToolApprovalResponse,
  stop,
  setMessages,
  regenerate,
  clearError,
} = useVendoThread(selectedThreadId);
```

The argument is named `selectedThreadId` above on purpose: the hook also
*returns* `threadId`, so destructuring into that name while passing it in is a
use-before-declaration error.

`setMessages` is what an edit-last affordance is built on: drop the last user
turn (and anything after) from the transcript, then refill your input from
that message so re-sending amends the turn instead of duplicating it. This is
the same flow the shipped chrome's **Edit** affordance uses.

```tsx
"use client";

import { useVendoThread } from "@vendoai/ui";

export function EditLastButton() {
  const { messages, setMessages } = useVendoThread();

  function editLast() {
    const lastUser = [...messages].reverse().find((m) => m.role === "user");
    if (!lastUser) return;
    setMessages(messages.slice(0, messages.indexOf(lastUser)));
    // refill your own composer input from lastUser
  }

  return <button onClick={editLast}>Edit last</button>;
}
```

The hook does **not** queue sends. Calling `sendMessage` mid-stream hands the
message straight to the AI SDK. The "type while it is answering, and it sends
when the reply lands" behavior belongs to the shipped chrome's composer,
which holds the draft and re-sends it on the busy edge — reproduce that in
your own composer by watching `status` if you want it.

## Apps export and import

`useApps` exposes `exportApp(appId)` and `importApp(bytes)` alongside the read
fields so a custom apps drawer can round-trip an `AppDocument` through the
wire without hand-rolling calls to `/apps/:id/export` and `/apps/import`.

```tsx
"use client";

import { useApps } from "@vendoai/ui";

export function AppsDrawer() {
  const { apps, error, isLoading, refresh, exportApp, importApp } = useApps();

  async function onExport(id: string) {
    const bytes = await exportApp(id);
    // save to disk, share, or hand to another user
  }

  async function onImport(file: File) {
    await importApp(new Uint8Array(await file.arrayBuffer()));
    // importApp already refreshed the list
  }

  // …render list, use error/isLoading as with any read hook
}
```

Import mints a fresh `app_` id and does not carry over data, grants, or
authority; see [Generated UI and apps](/concepts/generated-ui) for the
ownership model.

## Overlay control (useVendoOverlay)

`useVendoOverlay` gives your own chrome programmatic control over
`VendoOverlay` (the ready-made surface from `@vendoai/ui/chrome`). The
component's open state is uncontrolled by default and can be seeded with its
`defaultOpen` prop, or fully controlled with `open` and `onOpenChange`; the
hook wraps that controlled pair for you. Spread `overlayProps` onto the
component and call `open`, `close`, or `toggle` from your own shortcut or nav
button.

```ts
export interface VendoOverlayController {
  isOpen: boolean;          // whether the overlay is currently open
  open(): void;
  close(): void;
  toggle(): void;
  newConversation(): void;  // discard the current conversation, start fresh
  // Spread onto <VendoOverlay /> to hand it this controller's state:
  overlayProps: { open: boolean; onOpenChange(open: boolean): void; conversationKey: number };
}
```

`useVendoOverlay(options?)` accepts one option, `defaultOpen?: boolean`, and
returns the controller above. Pair it with `launcher="none"` when your host
owns the trigger, as with this Cmd/Ctrl+K shortcut:

```tsx
"use client";

import { useEffect } from "react";
import { useVendoOverlay } from "@vendoai/ui";
import { VendoOverlay } from "@vendoai/ui/chrome";

export function Assistant() {
  const overlay = useVendoOverlay();

  useEffect(() => {
    const onKey = (event: KeyboardEvent) => {
      if ((event.metaKey || event.ctrlKey) && event.key.toLowerCase() === "k") {
        event.preventDefault();
        overlay.toggle();
      }
    };
    document.addEventListener("keydown", onKey);
    return () => document.removeEventListener("keydown", onKey);
  }, [overlay.toggle]);

  return <VendoOverlay {...overlay.overlayProps} launcher="none" />;
}
```

The panel itself is portaled to `document.body`, locks page scroll, marks the
page behind the scrim `inert`, and restores focus to the invoking element on
close. Closing the overlay hides the panel without discarding the
conversation, so reopening within the same page session restores the prior
messages and thread. To start fresh, call `overlay.newConversation()`, use
the new-conversation button in the panel header, or bump the
`conversationKey` prop from your own state.

## BYO-agent embeds

If you run your own agent loop and spread in the
[guarded tool pack](/existing-agents), a separate set of components
(`VendoToolResult`, `VendoAppEmbed`, `VendoApprovalEmbed`) renders Vendo
inside that chat instead of these hooks. Import them from
`@vendoai/vendo/react`, which re-exports them — reaching for `@vendoai/ui`
directly works too, but only if you add that package as a direct dependency.
See [Embeds and envelopes](/existing-agents/embeds) for the full reference.

## When to use hooks vs. chrome

- Reach for `VendoOverlay` and the other chrome components when you want the
  shipped surface with brand tokens applied.
- Reach for hooks when you need to place counts, badges, or lists inside
  your own layout, or when your chrome needs to react to Vendo state without
  rendering the overlay at all.

Both paths speak the same wire, so mixing them in one app is safe.
