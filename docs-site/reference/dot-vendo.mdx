`.vendo/` is split by **author**, in three layers. Knowing which layer a file
belongs to tells you whether you may edit it and what can overwrite it:

| Layer | Written by | Files |
| --- | --- | --- |
| Machine | the deterministic scan (`vendo sync`) — regenerated wholesale | `tools.json`, `catalog.json`, `theme.extracted.json` (and `knowledge-manifest.json`, regenerated by the separate `vendo knowledge sync`) |
| Judgment | the AI pass — regenerated by the judge, never by a human | `judgments.json` |
| Human | you (init scaffolds some of them) — never overwritten | `overrides.json`, `policy.json`, `brief.md`, `design-rules.md`, `theme.json`, `knowledge.json` |

That split is the whole point: a re-sync can rewrite the machine layer and
re-judge the AI layer without ever clobbering a decision a person made.

| Path | Written by | Format |
| --- | --- | --- |
| `tools.json` | sync | `vendo/tools@3` (04) — each tool's descriptor and execution `binding`, plus inferred field `semantics`, `srcHash` (the handler-source hash incremental sync diffs against), `audience`, `outputSchema` when the source declares one, and `disabled` for anything extraction could not classify |
| `judgments.json` | sync (AI pass) | `vendo/judgments@1` (04) — the AI layer, keyed by tool name: `description`, `title`, `risk`, `critical`, `disabled`, `audience`, `semantics`. Hardenings apply themselves; loosenings only land here after a human accepted them |
| `overrides.json` | init / human | `vendo/overrides@3` (04) — per-tool overrides plus `compounds`, `briefs`, per-surface tool menus (`surfaces.agent` / `surfaces.mcp`, see [Curate the tool menu](/reference/mcp-door#curate-the-tool-menu)), and `remix.ignoreSlots` |
| `catalog.json` | sync | `vendo/catalog@1` (04) |
| `policy.json` | init / human | `vendo/policy@1` (05) |
| `remixable/<slot>.json` | sync | `PinBaseline` (06 §8) |
| `components/<Name>.json` | sync | `CapturedHostComponent` — one registered host component, refs only, no source ([Host components](/customize/host-components#what-sync-captures)) |
| `components/modules/<hex>.json` | sync | `CapturedModule` — `{ source, imports? }`, content-addressed by the sha-256 of its canonical JSON, so a module ten components share is stored once |
| `cloud.json` | sync (asked once) | `{ "pushComponents": boolean }` — this project's answer to "may registered-component source go to Vendo Cloud?" |

Commit `components/`. It is generated, but a missing local file is **not** a
deletion signal to the Cloud push (that rule is what keeps a half-written
capture from wiping the console's copy), so gitignoring it does not clean
anything up — it just hides drift. Size scales with distinct modules, not with
components: the demo host here stores 3 components in ~26 KB, and a
50-component registry over a shared design system lands in the low hundreds of
KB because every shared module and the app-root CSS are stored once. Mark it
`linguist-generated=true` in `.gitattributes` so reviews collapse it.
| `brief.md` | init | product brief for the system prompt (03 §3) |
| `design-rules.md` | host, optional | generation-time design rules (06 §5), re-read per generation so edits apply without a restart; `createVendo({ apps: { designRules } })` wins over it |
| `theme.json` | init extraction / human | `VendoTheme` |
| `theme.extracted.json` | init / sync | `vendo/theme-extracted@1` — what the deterministic scan produced last time. It is the merge base that lets sync tell "you edited this slot" from "the app's brand moved"; commit it beside `theme.json` |
| `knowledge.json` | `vendo knowledge add` / human | the registered knowledge sources (globs, kind, visibility, name) |
| `knowledge-manifest.json` | `vendo knowledge sync` | sha256 hashes of every synced document. Regenerable — safe to gitignore; deleting it re-syncs everything |
| `data/` | store | PGlite files |
| `data/.gitignore` | init | `*` plus an exception for itself — this is how `data/` stays out of git. Doctor warns (`E-CFG-002`) when it is missing |
| `data/misses.jsonl` | runtime | one `vendo/capability-miss@1` event per line ([Telemetry](/deploy/telemetry#capability-misses)) |
| `data/judge/` | sync (AI pass) | one raw artifact per judge stage. The directory is deleted and repopulated on every AI run, so it always reflects the last one and never accumulates |
| `data/extract/` | init / try | raw extraction-stage artifacts, same idea |

`data/` is runtime state and debugging residue, not configuration. Do not
commit it — the `.gitignore` init writes there is what keeps it out.

Five of these files are also **cloud-resolvable** surfaces:
`design-rules.md`, `brief.md`, `theme.json`, `policy.json`, and
`overrides.json`. Per surface, resolution is an explicit `createVendo` value →
the local file → the console's published value → unset, so the file's
existence is the switch. `vendo config status` shows which layer owns each
one; see [the CLI reference](/reference/cli#vendo-config-%3Ccommand%3E-dir).
`tools.json` and `catalog.json` are deliberately not on that list — they are
generation inputs, not host-editable content.

<Warning>
  **A local file silently out-ranks a console publish.** Nothing warns at
  runtime: the deployment keeps serving the local file and the publish is a
  no-op for it. And because init scaffolds `brief.md`, `policy.json`,
  `overrides.json`, and `theme.json`, a default install is file-owned on
  four of the five surfaces — `design-rules.md` is the only one the console
  owns out of the box. Publishing from the console without handing the
  surface over first is the classic "publishing looks broken" trap.

  - **Check who owns what:** `vendo config status` prints one owner per
    surface (`file`, `cloud`, `unset`); `vendo doctor` reports the same
    ownership.
  - **Hand a surface to the console:** delete the local file.
    `vendo config push <surface>` copies it into the console draft first
    (publishing stays a console step) and then offers the deletion; `--yes`
    deletes without asking.
  - **When a publish lands:** `brief.md` applies on the next agent turn and
    `design-rules.md` on the next app generation; `theme.json` and the
    tool-enablement half of `overrides.json` resolve boot-once, so they
    apply on the next restart (generation semantics from `overrides.json`
    are live); a cloud-owned `policy.json` is consulted live per guard
    check.
</Warning>
