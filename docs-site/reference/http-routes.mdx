The default base is `/api/vendo`. Bodies use core types encoded as JSON and
conversation turns stream over SSE.

Most routes resolve a principal through `principal(req)`. Exactly three
surfaces never call it, because each authenticates its own way: `/tick` by a
bearer secret, `/webhooks/*` by a signature, and `/box/*` by a per-app token.

The `/doctor/*` probes are a different case again — they *do* resolve a
principal (`/doctor/act-as/echo` calls the resolver directly; `/doctor/present`
reaches it through ordinary context resolution), but none of them *requires*
one. What keeps them off a deployment is mounting: like `/dev/*`, they are in
the route table only in a development composition (`createVendo({ development
})`, which `NODE_ENV=development` enables). Every other deployment answers
`404` because the route is not there, so nothing about the runtime or the
environment can open it. The lone exception is `/doctor/base-url`, mounted in
every environment by design: it reveals only whether `VENDO_BASE_URL` is set,
and production is exactly where that answer matters.

| Route | Method | Body → Response |
| --- | --- | --- |
| `/threads` | POST | `{ threadId?, message }` → AI SDK UI message stream (SSE), one conversational turn. The response carries `X-Vendo-Thread-Id: <thr_…>` (the effective requested or server-minted id) so hosts can persist the identity of a default thread without a follow-up round trip |
| `/threads` · `/threads/:id` | GET · GET/DELETE | thread summaries · thread |
| `/threads/:id/heartbeat` | POST | `{ active: boolean }`. Beaten by the client while a turn streams so the server can idle-abort the turn on a runtime that never surfaces a disconnect. Only the caller's own in-flight turns answer `true`; unknown and foreign ids answer `false` rather than revealing anything |
| `/approvals` | GET | pending `ApprovalRequest[]` |
| `/approvals/:id` | GET | one parked [BYO](/existing-agents) call's state, as a tagged envelope: `{state:"pending", request}` · `{state:"executed", outcome}` · `{state:"declined"}` · `{state:"expired"}`. Owner-scoped; unknown and foreign ids both answer `not-found`, on purpose |
| `/approvals/decide` | POST | `{ ids, decision }` → `{}`. Batch-capable, and a multi-id batch is atomic: every id lands or none does (members already decided the same way are skipped; an opposite prior decision conflicts the whole batch). Denying an automation's standing-grant ask also disarms that automation inside the same decision |
| `/grants` · `/grants/:id` | GET · DELETE | grants · revoke |
| `/apps` | GET · POST | list · `{ prompt }` → `AppDocument` |
| `/apps/:id` | GET · DELETE | app · delete |
| `/apps/:id/open` | GET | `OpenSurface`; with `?pending=1` a not-yet-servable app answers `{ kind: "pending" }` (HTTP 200) instead of a 404, the build-window poll `<VendoAppEmbed>` uses. A build that terminally failed — or a record owned by someone else — answers `{ kind: "failed", reason, retryable? }` at 200 so the poll resolves instead of spinning |
| `/apps/:id/ship-diff` | GET | `ShipDiff`, the reviewable code diff against the last approved baseline, hash-pinned to the current version. Owner-scoped. See [In-client venue](/concepts/in-client-venue). |
| `/apps/:id/call` | POST | `{ ref: "fn:<name>" \| "<tool>", args }` → `ToolOutcome` (tree actions + fn: calls) |
| `/apps/:id/edit` | POST | `{ instruction }` → `EditResult` |
| `/apps/:id/history` | GET | the app's capped version log, newest first |
| `/apps/:id/export` | GET | `.vendoapp` bytes |
| `/apps/import` | POST | bytes → `AppDocument` (fresh id minted). Requires `Content-Type: application/octet-stream` (or `application/vnd.vendo.app`) — it is exempt from the JSON CSRF floor, so a non-safelisted media type is what forces a cross-origin preflight |
| `/apps/:id/fn/:name` | POST | proxies one `fn:` call into the app's machine and relays its status, body, and `content-type`. No cookies or authorization cross the skin; a call that outruns the budget answers `504` while the box keeps working |
| `/apps/:id/machine/ping` | POST | → `{ state: "awake" \| "woke" }`. Re-arms the machine's idle timer for an embedded served app; `"woke"` tells the embed its URL is stale — re-open |
| `/apps/:id/fork` | POST | → `AppDocument` |
| `/apps/:id/rebase-pin` | POST | `{ slot }` → `PinRebaseResult`, re-fork from the new baseline and replay recorded intents, all-or-nothing |
| `/apps/fork-pin` | POST | `{ slot, instruction?, props? }` → `PinForkResult`, the Remix gesture on an empty slot (`props` is the wrapper's serializable live props at fork time, stored on the fork as its dashboard seed): deterministic engine fork of the captured slot into a freshly minted app (no model call); an optional instruction then rides the ordinary edit path scoped to the fork |
| `/apps/:id/fork-pin` | POST | `{ slot, instruction? }` → `PinForkResult`, the same gesture fork landing in an existing app |
| `/apps/placements` | GET | `?slots=a,b,c` (comma-separated) → `{ slot, app, title, status: "ready" \| "building" \| "failed" }[]`, one entry per named slot that currently holds an app for the caller. Registered ahead of the `/apps/:id/*` routes so `placements` is never read as an app id — the same ordering `/apps/fork-pin` needs. This is the ONE read every mounted `<VendoSlot>` on a page shares: one poll for the whole page, not one per slot |
| `/apps/:id/place` | POST | `{ slot }` → `{ evicted? }`, place this app in that slot for the caller. A slot holds one app per subject, so whatever it held is evicted and its id comes back in `evicted` |
| `/apps/:id/unplace` | POST | `{ slot }` → `{}`, empty the slot. The app itself is untouched, and unplacing a slot this app does not hold is not an error |
| `/slots` | POST | `{ slots: { id, label }[] }` → `{}`, the slot REGISTRY's write: which slots the caller's surfaces mount, as opposed to which app sits in one (`/apps/placements`). A slot is a prop on a host's own component, so nothing knows one exists until a page renders it — every render reports in, batched so a page costs one request rather than one per slot. Idempotent: one row per (subject, slot), refreshed in place, so a renamed label overwrites the old one |
| `/slots` | GET | `{ id, label, lastSeen }[]`, the caller's own registered slots, most recently seen first. Already filtered to the 30-day decay window — a slot that stopped rendering ages out on its own, since nothing announces a slot being taken off a page. Reporting it again brings it straight back |
| `/automations` | GET | list; each entry optionally carries `pendingGrants` (count of still-undecided standing-grant asks) and `grantSetId` — projected from the store so a reload still shows "waiting on N permissions" |
| `/automations/:id/enable` · `/disable` | POST | `{ enabled, missing, grantSetId? }` · `{}`; `grantSetId` names the ONE grant set the `missing` asks belong to (present exactly when `missing` is non-empty) — decide every member in one `POST /approvals/decide { ids }` and the whole set lands all-or-none |
| `/automations/:id/dry-run` | POST | `RunPlan` |
| `/runs` · `/runs/:id` | GET | run records |
| `/runs/:id/stop` | POST | `{}` |
| `/tick` | POST | scheduler tick (serverless cron target; requires `Authorization: Bearer <secret>`) |
| `/webhooks/:source` | POST | trigger ingress (Composio, host, plain), verified as described below. `source` is the **last** path segment and must equal the trigger's `connector` exactly. The mount is a raw prefix, so a deeper path still resolves — but only by its tail: `/webhooks/composio/gmail` ingests as source `gmail`, and a trigger registered as `composio/gmail` never fires. Keep sources to a single segment |
| `/activity` | GET | `AuditEvent[]`, self-scoped with `guard.audit.query({ principal })` |
| `/connections` | GET | connected accounts owned by the caller |
| `/connections/catalog` | GET | `{ available: { toolkit, connector, label?, description? }[] }` — the connectors this deployment advertises, wrapped in an envelope, not a bare array. What the connect dock resolves when the host passes no explicit `connectors` prop. An adapter that predates the catalog capability advertises `[]` rather than failing |
| `/connections/initiate` | POST | `{ toolkit, connector?, callbackUrl? }` → `{ id, connector, redirectUrl }`; refused for ephemeral and synthetic (`webhook:` / `vendo:`) subjects |
| `/connections/:id?connector=` | GET · DELETE | status (poll while connecting) · disconnect through the broker |
| `/orgs` · `/orgs/:id` and every other `/orgs/*` path | any | always `cloud-required` (`402`); organizations are a [Vendo Cloud](/deploy/vendo-cloud) capability, not an OSS wire route |
| `/status` | GET | `{ posture, version, blocks: {...} }`, includes `blocks.mcp` reporting the door posture (`"local"` when it serves its own OAuth surface, `"broker"` when an external authorization server fronts it, or `false` when the door is closed), `blocks.sandbox` reporting the execution venue (`"e2b"`, `"cloud"`, `"custom"`, or `false` when none is wired), and `blocks.connections` reporting the connected-accounts broker posture (`"byo"`, `"cloud"`, or `false`) |
| `/sync/impact` | POST | Development compositions only (`createVendo({ development })`, which `NODE_ENV=development` enables). Every other deployment answers `404`: the route is not in the table at all, so nothing about the runtime or the environment can open it. `{ tools: string[] }` → `{ impact }`, per-tool reference counts across enabled apps, enabled automations, and active standing grants. Accepts up to 200 tool names per call. It takes no principal and its counts are deployment-wide, which is precisely why a deployment that did not opt in must not carry it |

## Development routes

These routes answer only in a development composition
(`createVendo({ development })`, which `NODE_ENV=development` enables).
`/dev/inclient-approval` also refuses a principal marked `ephemeral: true`
(`401`) — approving a host-page mount is a host trust decision, and the flag
doesn't clear it even in dev. The review routes mask instead of erroring,
answering an empty queue or `not-found` so no caller can probe another
subject's pending work.

| Route | Method | Body → Response |
| --- | --- | --- |
| `/dev/inclient-approval` | POST | `{ appId, approvedBy? }` → the minted `InClientApproval` record. Pins the app's *current* `versionHash` as an in-client approval for the resolved principal; `approvedBy` defaults to `"local-dev"`. Production returns `404`. The Cloud console mints approvals in production; this route is the documented stand-in for local demos. See [In-client venue and approvals](/concepts/in-client-venue). |
| `/apps/review-queue` | GET | review-kind versions awaiting a reviewer, with requester, slot, version hash, submission time, resubmission count, and the ship-diff payload. Outside a development composition it answers an empty array, never an error. Without `createVendo({ apps: { review: { reviewer } } })` a caller sees only their own submissions |
| `/apps/:id/reject-review` | POST | `{ note }` → the rejection. The note is required (the user's panel renders it) and the work is not deleted; a new version supersedes the rejection. Takes the same reviewer assertion; every other caller gets the `not-found` an unowned app answers |

### Doctor probes

`vendo doctor` drives a handful of synthetic routes against the running dev
server. They are mounted by the same `development` flag the `/dev/*` routes
above use (`createVendo({ development })`, which `NODE_ENV=development`
enables), and on any other deployment they are not in the route table at all —
a plain `404`. None of them takes a principal, and `/doctor/machines` reports
across every subject, so mounting is the whole access control. The one
deliberate exception is `/doctor/base-url`, which reports a static composition
fact (is `VENDO_BASE_URL` set?) and answers in every environment, because
production is exactly where that answer matters.

| Route | Method | Purpose |
| --- | --- | --- |
| `/doctor/base-url` | GET | `{ ok: true }`, or `409` with `base-url-not-set-in-production`. Mounted in every environment |
| `/doctor/machines` | GET | which apps carry a machine, whether a schedule caller is configured, and each schedule's last-fired state |
| `/doctor/present` · `/doctor/present/echo` | POST · GET | mint and echo the present-mode credential round trip; the echo reports booleans only, never credential values |
| `/doctor/act-as` · `/doctor/act-as/echo` | POST · GET | mint `actAs` material and check the host's own principal resolver accepts it |

## Box callbacks

An app machine calls back into the host through `/box/*`, authenticated with
`Authorization: Bearer $VENDO_APP_TOKEN` — the per-app token minted at
provision. No cookie, no host principal: this surface is called from inside
the box, in any language. The routes and their bodies are documented with the
rest of the machine contract in
[the app machine environment](/reference/environment-variables#app-machine-environment).

## MCP door

With `createVendo({ mcp: true, oauth })`, the door serves its transport under
the wire plus four origin-root discovery documents through the same handler.
Bodies follow the MCP transport spec, not the wire's JSON envelope.

| Path | Method | Purpose |
| --- | --- | --- |
| `/api/vendo/mcp` | POST · GET · DELETE | MCP Streamable HTTP transport |
| `/api/vendo/mcp/authorize` | GET · POST | OAuth authorization endpoint; POST receives the door-owned consent form submission |
| `/api/vendo/mcp/token` | POST | OAuth token endpoint (form-encoded) |
| `/api/vendo/mcp/revoke` | POST | RFC 7009 token revocation (form-encoded). A revocation that lands — including one naming a token that no longer exists — answers an empty `200`, per the spec. Five paths answer `400` with an OAuth `{ error, error_description }` body instead: a non-form content type, a missing `token` or `client_id`, an unresolvable `client_id`, a token issued to a different client, and — the one that is not the caller's fault — a store whose records do not support atomic claims, which fails `server_error` no matter how well-formed the request was |
| `/api/vendo/mcp/register` | POST | OAuth dynamic client registration (JSON body) |
| `/api/vendo/mcp/federate` | GET | signed login handshake for an external authorization server; only mounted when `federation` is configured |
| `/api/vendo/mcp/connect` | GET | the door's one page for **people**, not clients: an HTML setup page naming the product and the door's public MCP URL, for pasting into an MCP client. Unauthenticated by design — no session, no token, and nothing on it that the public server card does not already carry. Titled with the host identity's name, and styled with the door's theme when the composition resolves one. Any method other than GET is `404` |
| `/.well-known/oauth-protected-resource/api/vendo/mcp` | GET | RFC 9728 protected-resource metadata |
| `/.well-known/oauth-authorization-server/api/vendo/mcp` | GET | RFC 8414 authorization-server metadata |
| `/.well-known/mcp/server-card.json` · `/.well-known/mcp-server-card` | GET | server card describing the door |

With `remoteAs` configured, `/api/vendo/mcp/authorize`, `/token`, `/revoke`, `/register`,
and the RFC 8414 authorization-server metadata all return `404`; the external
issuer owns those endpoints and RFC 9728 metadata advertises it. The transport
and `/connect` are unaffected — delegating the authorization server does not
take away the door's own setup page. See [MCP
door](/capabilities/mcp) for the delegation model.

Door paths bypass the wire's principal resolver and CSRF JSON gate. The door
re-resolves `oauth.principal(subject)` on every bearer-authenticated transport
request, so returning `null` revokes live sessions; the OAuth and discovery
endpoints are not principal-resolved. The origin-root discovery documents sit
outside `/api/vendo`; opting into MCP during `vendo init` generates the sibling
Next.js route that forwards them to the same handler. See [MCP
door](/capabilities/mcp) for the generated placement and manual fallback.

## Webhook verification

Every source registers verification during wiring. Connector sources use their
own signed headers. Self-minted sources use HMAC-SHA256 over
`id.timestamp.rawBody`, with signature, timestamp, and delivery id in headers.
The accepted clock window is five minutes. Delivery ids are deduplicated.

A verification failure returns 401, resolves no principal, starts no run, and
writes one audit event. The secret never appears in a URL.

## Organization context

Organizations are a [Vendo Cloud](/deploy/vendo-cloud) capability, not an
OSS wire feature. The entire `/orgs` route family, and an `?org=<orgId>`
query parameter (or `body.org`) on `/approvals` or `/grants`, always return
`cloud-required` (`402`), regardless of `VENDO_API_KEY`. See
[Principals](/deploy/principals-and-orgs).

## Errors and CSRF

Every non-2xx response uses `{ "error": { "code", "message" } }`; see
[Troubleshooting](/deploy/troubleshooting#error-codes) for the code-to-status
map.

Cookie-authenticated mutations require `Content-Type: application/json`. The
exceptions are exactly four: binary `/apps/import`, signed `/webhooks/:source`,
bearer-authenticated `/tick`, and the bearer-authenticated `/box/*` callback
surface. None of them carries ambient credentials, which is why the gate can
be skipped — each instead proves itself the way its own surface does:
`/apps/import` by demanding a non-safelisted media type, `/box/*` by
validating `application/json` on its JSON routes, `/webhooks/*` by signature,
and `/tick` by its bearer secret alone (it checks no content type). MCP door
paths sit outside both rules; they speak MCP and OAuth response shapes, not
the wire envelope.
