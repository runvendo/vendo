Import the default composition from `@vendoai/vendo/server`.

Type imports come from the umbrella, not the block packages. The root
`@vendoai/vendo` re-exports every type below that the blocks own, and only
`@vendoai/vendo` is a dependency your app actually declares — importing the
same type from `@vendoai/core` or `@vendoai/apps` is a `TS2307` under pnpm's
strict linking, because those are not your dependencies.

Two entries, and the split matters: `createVendo` lives at
`@vendoai/vendo/server` along with the types shaped specifically for its config,
while the bulk of the types — including `HostOAuthAdapter`, the type you need to
write the `oauth` adapter `mcp` requires — is on the **root** `@vendoai/vendo`.

```ts
import type {
  ActAs, ActionsRegistry, AppsRuntime, AutomationsEngine, ComponentCatalog,
  ComponentRegistry, Connector, ExtractedTool, FilesAdapter, Harness,
  HostOAuthAdapter, Json, KnowledgeAdapter, Principal, RunId, SandboxAdapter,
  SecretsProvider, Skill, ToolDefinition, ToolRegistry, VendoGuard, VendoStore,
  VendoTheme,
} from "@vendoai/vendo";
import type {
  ComposedAgent, ConnectionsService, CreateVendoConfig, GuardRules, HarnessTurns,
  HostAuthPreset, ModelsConfig, ServerActionHandler,
} from "@vendoai/vendo/server";
import type { LanguageModel } from "ai";                      // peerDependency (00 conventions)

export function createVendo(config: CreateVendoConfig): Vendo;

export interface Vendo {
  handler: (req: Request) => Promise<Response>;   // fetch-style; mount at /api/vendo/[...]
  emit(event: string, payload: Json, principal: Principal): Promise<RunId[]>;   // the host-event seam, re-exposed
  guard: VendoGuard; apps: AppsRuntime; automations: AutomationsEngine; actions: ActionsRegistry; connections: ConnectionsService; store: VendoStore;
  guardedTools: ToolRegistry;   // the guard-bound registry the BYO tool pack executes through; parks pending-approval calls for wire resume
  harness: HarnessTurns;        // the composed thinker's door: what POST /threads runs, and what a host driving a turn directly calls
}
```

One key in `CreateVendoConfig` is required — an identity, as either `principal`
or an `auth` preset (`oauth` becomes required when `mcp` is on). Day one is
`createVendo({ auth })`, and `.vendo/` — written by `vendo init` — supplies the
rest. `createVendo({ principal: async () => ({ kind: "user", subject: "dev" }) })` boots on an
env-resolved model and default persistence; `createVendo()` is a type error,
and `createVendo({})` throws `VendoError("validation")` naming the missing
identity.

When `principal(req)` resolves null, the request is refused with `forbidden`:
Vendo mints no principals of its own. A host that wants logged-out visitors
served resolves them to a principal of its own choosing — marking it
`ephemeral: true` keeps that principal out of org membership and blocks it from
connecting external accounts.

The composition registers app capability tools in actions and guard-binds every
tool registry passed to the harness, apps, and automations.

`handler` is framework-agnostic. `nextVendoHandler(vendo)` adapts it to a
Next.js route module. Mount it at `/api/vendo/[...]` unless the client uses a
different base URL.

`emit(event, payload, principal)` is the host-event seam. It returns the ids of
runs started for enabled automations owned by that principal.

## Values built by another function

Three slots take a value another exported function builds, and that is where
knobs a host might look for on `createVendo` itself actually live:

```ts
import { createVendo, guard, vendo } from "@vendoai/vendo/server";
import { agent } from "@vendoai/agents";

createVendo({
  auth,
  instructions: "Answer in the product's voice; never invent account numbers.",
  guard: guard({ policy: "cautious" }),   // the rules; this composition completes them
  harness: vendo({ maxSteps: 40 }),       // the thinker, and the thinker's own knobs
});
```

- **`guard`** takes `guard({ policy, judge, approvals })` — the deployment's
  rules — and this composition finishes them with the store, the app/service
  risk grading and the org-policy layer. A `VendoGuard` built by
  `createGuard({ store, … })` is taken verbatim instead. `policy`, `judge` and
  `approvals` were top-level `createVendo` keys and are gone: passing one now
  throws at boot naming this slot.
- **`harness`** takes the thinker, and the thinker's own per-turn knobs ride
  with it: `vendo({ maxSteps, historyWindow, maxOutputTokens, contextTokenBudget })`.
  These were a `createVendo({ agent: { … } })` options bag, which let a host
  configure the thinker through a key the thinker never saw; passing that bag now
  throws at boot naming each knob's new home. What the DEPLOYMENT curates —
  `instructions`, `toolOutputCap`, `maxInitialTools`, `loadout` — stays at the top
  level.
- **`agent`** takes a whole agent built by `agent()` from `@vendoai/agents`, not
  an options object. This deployment adopts what that agent already composed:
  its harness, store, blob adapter, sandbox and `instructions`. See
  [Use with your existing agent](/existing-agents).

## Config keys

Types only; each key's behavior is documented once, on
[Handler options](/reference/handler-options#composition-configuration).

| Key | Type | Notes |
| --- | --- | --- |
| `model` | `LanguageModel` | **deprecated** → `models.default`. Setting both is a boot error, not a precedence puzzle |
| `paint` | `{ model?: LanguageModel; disabled?: boolean }` | **deprecated**: the model half → `models.fill`; `disabled` remains the single-lane switch for app generation |
| `models` | `ModelsConfig` | the model seats, keyed by JOB: `{ default?, reviewer?, judge?, fill? }`, each a model-name string (resolved through the credential ladder) or an explicit ai-SDK `LanguageModel` (wins as-is). Every unset seat borrows `default` |
| `auth` | `HostAuthPreset` | one preset fills `principal` + `actAs` + `oauth`; mutually exclusive with all three — see [actAs presets](/connect/act-as-presets) |
| `principal` | `(req: Request) => Promise<Principal \| null>` | required unless `auth` fills the seam, and mutually exclusive with it; `null` → the request is refused with `forbidden` |
| `tools` | `readonly (ExtractedTool \| ToolDefinition)[]` | host-tool declarations in memory (else `.vendo/tools.json`), and/or executable tools — the two shapes are told apart by `execute` |
| `skills` | `readonly Skill[]` | SKILL.md values mounted at `/host/skills` for the harness to list cheaply and load on demand |
| `catalog` | `ComponentCatalog \| ComponentRegistry` | host components exposed to the generation prompt; see [Host components](/connect/host-components) |
| `theme` | `VendoTheme` | programmatic override for `.vendo/theme.json`, resolved once at compose |
| `instructions` | `string` | the prose this deployment puts in front of the agent every turn; the override for `.vendo/brief.md`. `brief` and `agent.instructions` were this same knob under two names and are gone |
| `store` | `VendoStore` | default `createStore()` (PGlite, `.vendo/data`); with `VENDO_API_KEY` and no `store` passed, the Cloud hosted store fills the slot |
| `files` | `FilesAdapter` | where workspace file content lives past 5 MiB; default: the store's own blobs |
| `sandbox` | `SandboxAdapter` | e.g. `cloudSandbox({ apiKey })`, `e2bSandbox({ apiKey })`; absent → auto-selected from `E2B_API_KEY` / `VENDO_API_KEY`, else tree-only apps |
| `harness` | `Harness` | WHO THINKS. Default `vendo()`; also `claudeCode()`, or your own via `defineHarness`. Carries the per-turn knobs — see [above](#values-built-by-another-function) |
| `knowledge` | `KnowledgeAdapter` | composes the `vendo_knowledge_search` tool; unset, that tool does not exist |
| `connectors` | `readonly (string \| Connector)[]` | one mixed list: a string names a Vendo Cloud toolkit (needs `VENDO_API_KEY`), a `Connector` object is an explicit provider used verbatim |
| `connections` | `ConnectionsService` | explicit connections adapter; always wins over the composed default |
| `actAs` | `ActAs` | escape hatch, mutually exclusive with `auth` |
| `serverActions` | `Record<string, ServerActionHandler>` | the map generated by `vendo sync`, keyed `"<module>#<exportName>"`; a missing key fails closed at execution |
| `guard` | `VendoGuard \| GuardRules` | the deployment's choke point as one value — see [above](#values-built-by-another-function) |
| `secrets` | `SecretsProvider` | default `envSecrets()` |
| `logger` | `VendoLogger` | one structured event per line Vendo would have written to the console; unset keeps those console lines |
| `telemetry` | `boolean` | wires `@vendoai/telemetry` |
| `development` | `boolean` | dev-only injection seams; `NODE_ENV=development` enables them, `false` disables that default |
| `profileDir` | `string` | the project root `.vendo/` is read under; unset keeps the process cwd |
| `fetch` | `typeof fetch` | the fetch host route/OpenAPI tool bindings execute through; unset keeps the platform fetch |
| `profile` | `{ overrides?, theme?, brief?, catalog?, policy?, designRules?, tools? }` | the `.vendo/` pieces as in-memory compose-time inputs, each winning over its file. `profile.tools` is **deprecated** → the `tools` slot |
| `mcp` | `boolean \| { baseUrl?: string; remoteAs?: object; federation?: object }` | opens the [MCP door](/capabilities/mcp); off by default |
| `oauth` | `HostOAuthAdapter` | escape hatch, mutually exclusive with `auth`; required when `mcp` is on and `auth` supplies no oauth half |
| `agent` | `ComposedAgent` | a whole agent built by `agent()` from `@vendoai/agents` — see [above](#values-built-by-another-function) |
| `sweep` | `{ intervalMs?: number }` | TTL-sweep cadence for expired parked BYO calls and stranded approvals; default 60 s |
| `toolOutputCap` | `number` | how much of one tool result reaches the model, in characters (default `32000`; `0` disables) |
| `maxInitialTools` | `number` | cap on the uncurated initial tool loadout (default `128`); the rest stay discoverable via `find_tools` |
| `loadout` | `readonly string[]` | explicit curated initial loadout, by tool name |
| `apps` | `false \| { designRules?, pipeline?, checks?, review? }` | `false` unmounts app generation entirely; otherwise the apps-block options |
| `automations` | `false` | `false` unmounts automations: `/automations`, `/runs` and `/webhooks` answer not-found and `vendo.emit` refuses |

## `eraseStore`

`@vendoai/vendo/server` re-exports `eraseStore(store)`, the sanctioned
deletion path across every store table. It is the only supported way to
delete rows from the append-only `vendo_audit` table.

```ts
import { eraseStore } from "@vendoai/vendo/server";

await eraseStore(vendo.store).bySubject("user_123");
await eraseStore(vendo.store).byApp("app_abc");
```

Each call returns a map of per-table deleted counts. See
[Persistence](/deploy/persistence#erasing-data) for the full semantics.

## BYO-agent subpaths

Two subpath exports build the guarded Vendo tool pack for a host that keeps
its own agent loop. Both are thin shims over one framework-neutral core;
every pack tool executes through `vendo.guardedTools`, the same guard-bound
registry Vendo's own loop uses.

```ts
// @vendoai/vendo/ai-sdk: AI SDK ToolSet, built per request
export function vendoTools(
  vendo: Vendo,
  options: { principal: Principal; sessionId?: string; include?: string[]; exclude?: string[] },
): Promise<ToolSet>;

// @vendoai/vendo/mastra: Mastra createTool shapes for Agent({ tools });
// the principal resolves per call from Mastra's request context
export function vendoMastraTools(
  vendo: Vendo,
  options?: { include?: string[]; exclude?: string[] },
): Promise<Record<string, VendoMastraTool>>;

export const VENDO_PRINCIPAL_KEY = "vendo-principal"; // required per request; missing fails closed
export const VENDO_SESSION_KEY = "vendo-session-id";  // optional audit continuity
```

`include`/`exclude` match final (namespaced) tool names exactly; `exclude`
wins. `@mastra/core` is an optional peer dependency used only by the
`./mastra` subpath. Tool outputs are the versioned envelopes documented in
[Embeds and envelopes](/existing-agents/embeds#the-envelope-contract).
