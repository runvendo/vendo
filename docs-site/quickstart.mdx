Vendo setup is one command. `npx vendo init` scans your app, scaffolds the
entire server side, and prints the one paste that mounts the visible agent
surface — `<VendoRoot>` plus `<VendoOverlay />` — in your layout. Start the
dev server and send a turn.

<Note>
  Vendo's built-in agent is in beta. Most teams should bring their own agent:
  keep the loop you already run and spread Vendo's tool pack into it. Jump
  straight to the [AI SDK](/existing-agents/ai-sdk) or
  [Mastra](/existing-agents/mastra) quickstart. This page wires Vendo as the
  whole agent, loop and UI included.
</Note>

## Install and init

```bash
npm install @vendoai/vendo
npx vendo init
```

<Note>
  Right after a Vendo release, package managers with a release cooldown hold
  the new version back. pnpm 11 (`minimumReleaseAge`, one day by default)
  fails loud with "no versions available"; npm's opt-in `min-release-age`
  instead resolves silently to the newest version old enough to pass, and
  `vendo init` pins that stale version in `package.json`. Check what you
  actually got:

  ```bash
  npm ls @vendoai/vendo
  ```

  To take the current release anyway, pass `--min-release-age=0` on npm, or
  exclude Vendo in `pnpm-workspace.yaml`:

  ```yaml
  minimumReleaseAgeExclude:
    - vendoai
    - "@vendoai/*"
  ```
</Note>

Init runs no interview: there are no keys to paste and no per-diff approvals.
An interactive run stops for seven decisions, all Enter-to-accept — the
detected auth preset, the Vendo Cloud starter-key offer, consent for the AI
judgment pass, one aggregated review if that pass proposes loosening a risk
grade, a `zod` bump when your pin is below 3.25, any theme slot the extractor
is unsure of, and a closing "star the repo?" — and `--yes` answers every one
of them. It detects your framework and auth from `package.json`, then writes
everything Vendo needs:

- the catch-all route `app/api/vendo/[...vendo]/route.ts` holding the whole
  `createVendo` composition
- an empty component registry, `vendo/registry.tsx`, for the branded
  components the agent may render
- the client mount `vendo/vendo-root.tsx` — a `"use client"` wrapper that
  applies your registry and theme and mounts `<VendoOverlay />`, the visible
  launcher pill + panel
- one paste for you, printed in a framed block at the end of the run: the
  import plus wrapping `{children}` in that wrapper in `app/layout.tsx`. Init
  never edits a file you authored, and `vendo doctor` fails until this lands —
  it is what puts the agent on screen
- your API extracted into `.vendo/tools.json`, and any `"use server"` actions
  registered as agent tools through a generated `vendo-actions.ts` map (plain
  route scanning reads Next.js conventions today; on Express, Fastify, or
  Hono, API tools come from an OpenAPI spec, a tRPC router, or a GraphQL
  schema)
- your brand extracted into `.vendo/theme.json`
- a model key: if no provider key is set, init offers a metered Vendo Cloud
  starter key inline

The full inventory and how detection decides:
[vendo init](/connect/vendo-init).

The generated route is yours to read and change, but there is nothing left to
write. The scaffold looks like this:

```ts
// app/api/vendo/[...vendo]/route.ts — equivalent to what `vendo init` writes
// (init emits a relative registry import; the `@/*` alias reads better here)
import { authJs } from "@vendoai/vendo/auth/auth-js";
import { createVendo, guard, nextVendoHandler } from "@vendoai/vendo/server";
import { serverActions } from "./vendo-actions";
import { registry } from "@/vendo/registry";

const vendo = createVendo({
  auth: authJs(),    // detected from package.json
  catalog: registry, // the components the agent may render
  serverActions,     // generated when "use server" actions are detected
  guard: guard({ policy: {} }), // .vendo/policy.json: destructive asks, reads run
});

export const { GET, POST, PUT, PATCH, DELETE } = nextVendoHandler(vendo);
```

Every key is optional, and there is no `model` line on purpose: a bare
`createVendo()` resolves a model from the environment and defaults to
anonymous ephemeral sessions and PGlite persistence. The eight slots the
surface is built from — `auth`, `tools`, `skills`, `harness`, `models`,
`store`, `files`, `sandbox` — all default or degrade honestly, and every key
lives in [Handler options](/reference/handler-options).

The handler takes a standard `Request` and returns a standard `Response`, so
it runs in Next.js, Express, Fastify, Hono, Bun, or any Node-compatible
runtime (Node 20 or later); non-Next wiring is
[below](#wire-the-express-adapter).

## The client mount

Init generates the visible surface for you: `vendo/vendo-root.tsx` is a
`"use client"` boundary that owns the registry and theme imports and mounts
`<VendoOverlay />`. Your paste wraps the app in it. The generated wrapper
looks like this — it is yours to change:

```tsx
// vendo/vendo-root.tsx (generated by `vendo init`)
"use client";

import { VendoOverlay, VendoRoot as VendoClientRoot } from "@vendoai/vendo/react";
import type { ReactNode } from "react";
import { registry } from "./registry";
import theme from "../.vendo/theme.json";
import type { VendoTheme } from "@vendoai/vendo";

export function VendoRoot({ children }: { children: ReactNode }) {
  return (
    <VendoClientRoot components={registry} theme={theme as VendoTheme}>
      {children}
      <VendoOverlay />
    </VendoClientRoot>
  );
}
```

Init prints the one paste that remains, naming your layout file and the exact
lines:

```tsx
// app/layout.tsx
import { VendoRoot } from "../vendo/vendo-root";

// then wrap the app:
<VendoRoot>{children}</VendoRoot>
```

<Warning>
  Keep the registry import inside the `"use client"` wrapper. Importing the
  registry in the Server Component layout and passing it to the provider
  crashes React Server Components serialization once the registry holds real
  components — every page 500s.
</Warning>

The `theme` prop applies the brand init captured; the cast narrows
TypeScript's widened JSON-module string literals.

## Tune the overlay

`VendoOverlay` (from `@vendoai/vendo/react`, or `@vendoai/ui/chrome`) is the
ready-made agent surface: a brand-styled launcher pill plus a dialog panel
over your product. Move the launcher with `launcher="bottom-left"`, or set
`launcher="none"` and drive it yourself with the `useVendoOverlay` hook; see
[Overlay control](/reference/hooks#overlay-control-usevendooverlay). Prefer a
different surface entirely? Swap `<VendoOverlay />` inside the generated
wrapper for your own composition, or for `<VendoThread />` — that one lives in
`@vendoai/ui/chrome` and needs `@vendoai/ui` as a direct dependency.
`<VendoOverlay />` is the only standalone chrome surface `@vendoai/vendo/react`
re-exports; the BYO embeds (`<VendoToolResult>`, `<VendoAppEmbed>`,
`<VendoApprovalEmbed>`) and every hook come from there too.

## Send the first turn

Start your dev server, open the overlay, and ask for a view, such as "Show my
overdue invoices by customer." Then gate on doctor:

```bash
npx vendo doctor
```

Doctor checks the wiring, makes one live `/status` round trip, and runs live
HTTP probes that confirm present-mode credentials forward and that `actAs`
(if configured) mints material your host accepts. See the
[CLI reference](/reference/cli#vendo-doctor-dir) for probe details.

One requirement before you ship: production must set `VENDO_BASE_URL` to the
app's public origin, or a tool call that needs credentials fails loud instead
of running unauthenticated. Init writes a `http://localhost:3000` default
into `.env.example`; see
[Environment variables](/reference/environment-variables#host-process).

## Wire the Express adapter

On Express, `vendo init` writes `vendo/server.ts` holding the same
`createVendo` composition plus a Node HTTP-to-fetch adapter, and two pastes
remain instead of one. Mount the adapter under one base path, and wrap the
client root:

```ts
import express from "express";
import { mountVendo } from "./vendo/server.js";

const app = express();
app.use("/api/vendo", mountVendo());
app.listen(3000);
```

```tsx
import { VendoOverlay, VendoRoot } from "@vendoai/vendo/react";
import { registry } from "./vendo/registry";
import theme from "./.vendo/theme.json";

root.render(
  <VendoRoot components={registry} theme={theme}>
    <App />
    <VendoOverlay />
  </VendoRoot>,
);
```

`vendo doctor` reports broken until both pastes are done.

### Other runtimes

On Fastify, Hono, Bun, Deno, Cloudflare Workers, or Lambda, run `vendo init
--framework custom`: it writes a runtime-neutral `vendo/server.ts` exporting
`handleVendoRequest(request, env)`, which every adapter mounts in one line —
see [Edge runtimes](/deploy/edge-runtimes). If you mount `vendo.handler`
under a base path yourself instead, your adapter must:

- Pass every method (GET, POST, PUT, PATCH, DELETE) through unchanged.
- Preserve streaming for `POST /threads`, never buffering the response body.
- Reconstruct the request URL from `req.originalUrl`, not `req.url`, when mounted
  with `app.use` on a base path (Express strips the mount path from `req.url`).
- Keep cookie and authorization headers available to `principal(request)` and to
  present-mode same-origin tool calls.
- Return multi-value `Set-Cookie` as a header array, not a joined string.
