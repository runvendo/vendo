Every wire request resolves a `Principal` through the `principal(req)` seam
you pass to `createVendo` — required, since Vendo mints no identity of its
own. The returned `subject` scopes threads, apps, approvals, grants,
activity, and runs across the whole composition. Returning `null` refuses
that request with `forbidden` (403): the visitor has no identity.

## Resolving a principal

```ts
principal: async (request) => {
  const user = await resolveSession(request);
  return user ? { kind: "user", subject: user.id } : null;
},
```

Returning `null` refuses the request with `forbidden` (403) — the visitor
has no identity. Anything else, a signed-in user's stable id, scopes that
request's data to the returned subject for good.

## Identity reference

### Principal kinds

`Principal.kind` is `"user"` or `"org"`. Your `principal(req)` resolver may
only return `kind: "user"`: the wire rejects a resolver-produced
`kind: "org"` principal loudly, since organization context is a
[Vendo Cloud](/deploy/vendo-cloud) capability, never something an OSS host
resolves directly.

### The reserved `vendo:` namespace

Subjects that start with `vendo:` are reserved for Vendo-owned identities.
Two are defined today:

- `vendo:webhook:<source>`: webhook deliveries execute under this subject
  when no principal is otherwise attached to the request.
- `vendo:org:<orgId>`: reserved for [Vendo Cloud](/deploy/vendo-cloud)
  organization workspaces. The OSS wire never mints this subject itself;
  every `/orgs` route (and any org-scoped query on `/approvals` or
  `/grants`) answers `cloud-required` (HTTP 402) unconditionally.

A `principal(req)` resolver that returns a `vendo:*` subject, or a
`kind: "org"` principal, is rejected at the wire with a `validation` error.
Mint your own subjects under whatever prefix your product uses (for example
`user:`); leave the `vendo:` prefix alone.

If you have audit readers or dashboards that filter on webhook subjects,
update them to match `vendo:webhook:<source>` instead of the bare
`webhook:<source>` form.

### Organizations are a Vendo Cloud capability

Sharing apps, approvals, and grants under one org subject is not an OSS wire
feature. The self-hosted wire always answers every `/orgs` route, and any
`/approvals` or `/grants` request carrying an `org` param, with
`cloud-required` (HTTP 402), regardless of `VENDO_API_KEY`. `/status`
reports no `orgs` block.

Organization workspaces live in [Vendo Cloud](/deploy/vendo-cloud), which
manages its own accounts, members, and keys server-side. See that page for
the Cloud-side org model (`vendo cloud whoami`, `vendo cloud members`, and
key scoping by `--org`).
