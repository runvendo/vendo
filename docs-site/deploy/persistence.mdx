Vendo persists threads, apps, records, blobs, state, grants, approvals,
audit, runs, and secrets in one Postgres-compatible store. Local dev uses an
embedded PGlite database with the same schema; production points the same
store at your own Postgres.

<Warning>
  **Next.js hosts must externalize PGlite.** Webpack-bundling it breaks its
  filesystem access (`The "path" argument must be of type string … Received
  an instance of URL`) and takes the whole wire down. Add to
  `next.config.*`:

  ```js
  serverExternalPackages: ["esbuild", "@electric-sql/pglite"]
  ```

  Every Vendo example carries this line; a host using the local store —
  including the zero-config dev default — needs it too.
</Warning>

## Configuring a store

```ts
export function createStore(config?: {
  url?: string;
  dataDir?: string;
  encryption?: { key: string };
}): VendoStore;
```

Omit `url` for PGlite. `dataDir` defaults to `.vendo/data`. Set `url` for a
hosted Postgres database. Both use the same schema and migration path.

The PGlite default applies only while no `VENDO_API_KEY` is set. See
[Vendo Cloud](/deploy/vendo-cloud#hosted-store) for what setting the key
does to where your data lives and how adapter precedence works.

All structured payloads use `jsonb`. App record refs are GIN-indexed and can
be joined to host tables with containment queries. Collection names use
`app:<appId>:<name>`.

App machines reach `vendo_records` through the app-token `/box` callback
surface, not directly. Box-written rows land in their own namespace,
`app:<appId>:box:<collection>`, capped at 256 KB per row. App-declared
storage collections (`app:<appId>:<name>`; records 256 KB, blobs 5 MB, the
reserved name `state` rejected, every written `refs` key declared with a
non-empty string value) are served by the apps runtime for tree apps and
host tools. See the [app machine
environment](/reference/environment-variables#app-machine-environment) for
the `/box` callback routes.

`encryption.key` encrypts secret values in `vendo_secrets` only. App records
stay queryable.

## Store reference

### Stable tables

The fifteen stable public tables are `vendo_meta`, `vendo_apps`,
`vendo_records`, `vendo_blobs`, `vendo_state`, `vendo_threads`,
`vendo_grants`, `vendo_approvals`, `vendo_audit`, `vendo_runs`,
`vendo_secrets`, `vendo_mcp_clients`, `vendo_mcp_grants`,
`vendo_knowledge_docs`, and `vendo_knowledge_chunks`. `eraseStore` covers all
fifteen.

### PGlite is single-writer

The store enforces one live instance per data dir with a lock file inside it
(`<dataDir>/.vendo-writer.lock`). A second process pointed at the same dir
waits for the holder to exit instead of opening (and corrupting) it: dev
servers that evaluate your server module in extra worker processes are
safe. A lock left behind by a killed process is reclaimed automatically. If
boot logs show the store waiting on a pid, another server owns that dir:
stop it, give each server its own `dataDir`, or move to a Postgres `url`.

### Ephemeral container filesystems wipe PGlite on redeploy

Container platforms with long-lived processes (Railway, Render, Fly.io,
Heroku) let PGlite run happily, then recreate the container filesystem on
every redeploy. The store keeps working right up to that point, and then
every app your users built and every row of their data is gone. The same
loss applies to any `dataDir` under `/tmp`.

At boot the store adds a warning row to the `vendo ready` block whenever it
composes a PGlite engine writing to one of those places:

```text
◆  vendo ready
│  ✓ sandbox   cloud    VENDO_API_KEY
│  ✓ store     local    .vendo/data
│  ✓ models    cloud    VENDO_API_KEY (gateway)
│  ⚠ store     .vendo/data is on Railway's container filesystem — data will not survive a redeploy.
│              Mount a volume, or pass url: "postgres://…" to createVendo.
```

The trigger is any of the platform markers `RAILWAY_ENVIRONMENT`, `RENDER`,
`FLY_APP_NAME`, or `DYNO` in the environment, or a `dataDir` that resolves
under the OS temp dir or `/tmp`. `vendo doctor` reports the same finding
statically as [`E-STORE-001`](/deploy/troubleshooting#E-STORE-001).

Two ways out:

- **Mount a persistent volume** and point `dataDir` at it. This keeps
  PGlite as the engine, which is fine for smaller deployments:

  ```ts
  createVendo({
    store: createStore({ dataDir: "/data/vendo" }),
  });
  ```

- **Move to Postgres.** Pass a connection string as `url` and the store
  uses the Postgres engine instead of PGlite:

  ```ts
  createVendo({
    store: createStore({ url: process.env.DATABASE_URL }),
  });
  ```

The warning is silent for a Postgres `url`, `memory://`, a `dataDir` on a
real disk, the Cloud [hosted store](/deploy/vendo-cloud#hosted-store), and
any custom store adapter — only the local PGlite default can hit it.

Fully serverless platforms (Vercel, Cloudflare Pages, AWS Lambda) are a
harder case: PGlite refuses to boot there at all. See [edge
runtimes](/deploy/edge-runtimes) for what that refusal looks like.

### Encryption is opt-in, and production fails closed without it

Encryption covers exactly one column, `vendo_secrets.ciphertext`. Everything
else stays host-queryable plaintext by design.

What actually gates it is the store's own `allowUnencryptedSecrets` option:
with no encryption key and no explicit opt-in to plaintext, reading or writing
a secret value throws. `createStore({})` by hand therefore refuses secrets
even in development. Deleting and listing secrets keep working without a key —
neither touches ciphertext.

The default composition — no `store` passed to `createVendo` — supplies that
opt-in for you from the environment. Set a 32-byte base64 key at
`VENDO_STORE_ENCRYPTION_KEY` in your host `.env` and secrets encrypt. Without
it, the composition passes `allowUnencryptedSecrets` when `NODE_ENV` is not
`production`, so:

- In dev, secrets are written **unencrypted** under the gitignored data dir,
  and the first plaintext write logs a warning.
- In production, reading or writing a secret value **throws**. Set the key
  before you deploy anything that stores a secret.

An explicitly configured store always wins. If you pass
`store: createStore({ encryption: { key } })` to `createVendo`, the
environment variable is ignored — and so is the `NODE_ENV` convenience above.

Ciphertext is AES-256-GCM and bound to the secret name as authenticated data,
so a tampered or swapped row fails to decrypt. Do not rotate the key by hand:
losing it makes existing secrets unreadable. Encryption needs the Node
runtime — see [edge runtimes](/deploy/edge-runtimes).

### Audit is append-only

`vendo_audit` is write-once. Calling `put` with an existing id fails with
`conflict`, and `delete` is refused with `blocked`. The only sanctioned way
to remove audit rows is the erase API below.

### Ownership flips are refused

`vendo_apps`, `vendo_grants`, and `vendo_threads` all reject same-id writes
that move a row to a different subject. If you need to transfer ownership,
delete the row and re-seed it under the new subject.

### Erasing data

`eraseStore(store)` is the sanctioned deletion path for `vendo_audit`,
cascading across every store table. Use it for right-to-erasure requests,
tearing down a test app, or purging old runs.

```ts
import { eraseStore } from "@vendoai/vendo/server";

// Full erasure for a subject across every store table.
const bySubject = await eraseStore(vendo.store).bySubject(subjectId);

// Erase everything owned by one app.
const byApp = await eraseStore(vendo.store).byApp(appId);
```

Each call returns per-table deleted counts so you can log or verify the
cascade.

Against the [hosted store](/deploy/vendo-cloud#hosted-store), `eraseStore`
calls `POST /api/v1/store/erase`, which requires an **admin-scoped**
`VENDO_API_KEY`. A runtime-scoped key is refused with HTTP 403 and the
`blocked` code before the request body is read — the same refusal applies to
the lifecycle promote door. Existing keys default to the runtime scope, so
minting a new admin key in the console is a hard prerequisite for calling
`eraseStore` against Vendo Cloud. Mint one from your project's Keys page in
the console: the **Create key** dialog shows a Runtime / Admin picker, and
Admin is a deliberate second click. See [API key
scopes](/deploy/vendo-cloud#api-key-scopes) for the full list of doors each
scope opens. Against a local PGlite or your own Postgres, `eraseStore` runs
directly against the store and no scope check applies.

### Compare-and-set on your own collections

When two ticks, retries, or agent runs might race on the same record, a
record store exposes optional compare-and-set primitives on the collection
handle: `records(name).claim(expected, replacement?)` returns `true` for the
single caller whose read of `expected` still matched, and
`records(name).atomic?.insertIfAbsent(record)` /
`.compareAndSwap(record, expectedRevision)` return `null` when another caller
won. Your own collections expose both. Vendo's internal tables vary — the
routed reserved tables expose no `claim` at all — so feature-detect the
method on the handle rather than assuming it is there.
