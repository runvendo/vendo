Vendo collects three separate streams: build and development telemetry,
runtime SDK telemetry, and capability-miss events. Each has its own consent
model.

## Build and development telemetry

Build and development telemetry runs in build and development tooling. It does
not fire from a deployed production app and does not collect end-user product
activity.

It has two lanes:

- **Anonymous** (the default): events carry a random anonymous id plus
  allowlisted counts and short enums, and a salted one-way hash of the git
  origin URL (or package name) so events from the same repo group together.
- **Cloud**: a well-formed `VENDO_API_KEY` additionally marks every event
  with `cloud: true` and the SHA-256 hash of the key — joinable to the owning
  account in the Vendo console — and may add the project name, repo host
  classification, setup counts, init timings, and a scrubbed error detail.
  The raw key itself is never sent.

Events never contain source, file paths, prompts, generated UI, tool inputs
or outputs, keys, environment values, request bodies, raw error messages, or
stack traces. The cloud lane's `errorDetail` is the only free-text property
ever sent, and it is scrubbed first: file paths, email addresses, and
secret-shaped strings are replaced with fixed tokens, then the result is
capped at 200 characters.

Disable this stream with any of these controls — each applies to both lanes,
so an opted-out user with a cloud key sends nothing:

- `VENDO_TELEMETRY_DISABLED=1` (or `true`)
- `DO_NOT_TRACK=1` (or `true`)
- `CI` set to anything other than `""`, `"0"`, or `"false"`
- `"optedOut": true` in `~/.vendo/telemetry.json`

`NODE_ENV` is a separate, narrower gate. It applies only to the dev-server
runtime collector, which fires solely when `NODE_ENV` is `development` or
`test` — an unset or unrecognized value is treated as production and
collects nothing. It does **not** gate the CLI and build collector, which is
what `vendo init`, `sync`, and `doctor` report through; use the four controls
above for that.

The stored id is a random UUID and is not derived from a machine, account,
project, or host app. Deleting the file rotates it.

The full event allowlist and cloud-lane property set are maintained in the
repository's
[`TELEMETRY.md`](https://github.com/runvendo/vendo/blob/main/TELEMETRY.md),
the authoritative document.

## Runtime SDK telemetry

Runtime SDK telemetry is what a deployed Vendo instance reports about
**itself** — which adapters it booted with, how a turn went, and whether
Vendo's own code warned or failed inside your process. It fires from a running
deployment (not just build and development tooling) and is uploaded to
`https://console.vendo.run/api/v1/telemetry` on the same terms the
capability-miss stream uses.

The stream never bills. The console's ingest door omits the `meter` option
that every billable endpoint declares, so events forwarded here can never
appear on an invoice.

### When it uploads

Uploads happen only when both of these hold:

- `VENDO_API_KEY` is set to a non-empty value
- the environment does not trip a kill switch (see [Opting out](#opting-out))

A keyless deployment installs no sink at all: `emitUsage` stays a no-op, and
nothing is queued or sent. This matches the capability-miss consent model, so
opting one stream out via env opts the other out too.

The console can also stop a talking deployment mid-flight. If your org has
`telemetry_disabled` set, the door answers `202 {accepted: 0, disabled: true}`
and the SDK stops uploading for the rest of the process lifetime.

### The five events

The event catalog is closed. A sixth event, or a new property on an existing
one, is a contract change on both the SDK and the console — never a silent
addition. Events carry shapes, counts, and names only: never a prompt, a tool
argument, a file, a row, a message, or a person.

| Event | Fires when | Properties |
| --- | --- | --- |
| `deployment_boot` | `createVendo` finishes composition | `adapters` (names of filled slots: `store`, `files`, `sandbox`, `secrets`, `harness`, `connections`, plus `knowledge` / `connectors` when mounted), `blocks` (`apps`, `automations`, `knowledge`, `mcp`), `framework` (`"next"` when `NEXT_RUNTIME` is set, otherwise `null`) |
| `agent_run` | one agent turn ends (success or error) | `durationMs`, `steps`, `toolCalls`, `tools` (sorted names), `modelFamily` (the model id the thinking seat resolved to, or `null` for a BYO brain like `claudeCode()`), `outcome` (`"ok" \| "error" \| "refused"`), `errorCode` |
| `guard_decision` | the guard renders a decision, beside its audit row — never in place of it | `kind`, `decision`, `tool` |
| `sdk_error` | Vendo's own logger emits a `warn` or `error` | `code`, `level`, `message` (Vendo's authored sentence), `data` (each logged key's shape only, never its value), `stack` (`@vendoai` frames only — host frames are stripped), `runtime` |
| `app_generated` | one app generation finishes | `components` (uses per component name), `durationMs`, `outcome` (`"ok" \| "error"`), `kind` |

### How each event is stamped

Every upload carries:

- `sdk_version` — the running SDK version, from the `@vendoai/vendo` package
- `runtime` — the JS runtime name: `workerd`, `edge-light`, `bun`, `deno`,
  `node`, or `unknown`, from the globals each runtime advertises
- `deployment_version` — resolved by the console from the
  `x-vendo-deployment-version` identity header (see [Deployment identity
  headers](#deployment-identity-headers) below)

Deployment identity (`org`, `project`, `deployment`) is stamped by the
console from the API key's scope and the identity headers — it never rides
the request body, so a deployment cannot claim to be another one.

### Routing SDK logs

Every `warn` or `error` Vendo writes to the operator log becomes an
`sdk_error` event as well. The console log line is untouched: host output
stays byte-identical whether or not the events stream is installed.

To route those log lines somewhere other than the console, pass a
[`logger`](/reference/handler-options) to `createVendo`:

```ts
import { createVendo } from "@vendoai/vendo/server";
import type { VendoLogger } from "@vendoai/core";

const logger: VendoLogger = (event) => {
  myObservability.record({
    level: event.level,
    code: event.code,
    message: event.message,
    data: event.data,
  });
};

const vendo = createVendo({
  // model, principal, store, ...
  logger,
});
```

A host-passed `logger` always wins. Unset keeps today's console lines,
unchanged. Either way, `warn` and `error` events are still reported as
`sdk_error` when a Cloud key is present and no kill switch is tripped.

### Deployment identity headers

Every key-authed request from a running deployment carries three identity
headers:

- `x-vendo-deployment-host` — the OS hostname, or `"unknown"` on edge and
  Worker targets that have no hostname
- `x-vendo-deployment-name` — the deployment name resolved from the
  project root
- `x-vendo-deployment-version` — the running `@vendoai/vendo` version

Operators reading request logs will see the `x-vendo-deployment-version`
header on every hosted call, including the ones the runtime SDK telemetry
stream itself makes.

### Opting out

The runtime SDK telemetry stream uses the same three environment kill
switches as capability-miss uploads:

| Variable | Blocks upload when |
| --- | --- |
| `VENDO_TELEMETRY_DISABLED` | equal to `"1"` or `"true"` |
| `DO_NOT_TRACK` | equal to `"1"` or `"true"` |
| `CI` | set to any value other than `""`, `"0"`, or `"false"` |

Any of these makes `createSdkEvents` return `undefined`, no sink is installed,
and `emitUsage` stays a no-op. The console's org-level `telemetry_disabled`
flag is a fourth control: the ingest door answers `disabled: true` and the SDK
stops uploading for the rest of the process lifetime.

## Capability misses

Capability misses record moments when the agent could not complete a user
request with the tools you exposed. Each event follows the
`vendo/capability-miss@1` contract and fires in exactly three cases:

- no tool in the extracted tool surface matched the intent
- the same tool failed at least twice in order and the agent stopped retrying
- the agent explicitly gave up

Each event carries a stable event and time identity, host and app context, the
session and thread, a privacy-scrubbed intent string, the exact tool surface
identity that was in scope, and the considered or attempted tools with
scrubbed failure detail.

Raw tool arguments and outputs never appear in the event. Credentials and
secrets are redacted, and unrelated personal data is minimized before write.

### Local persistence

The OSS runtime always appends one JSON object per line to
`.vendo/data/misses.jsonl` on the host machine. Writes are fire-and-forget:
sink failures never alter the agent turn, and the local file is not
consent-gated. Treat it as runtime state, like the rest of `.vendo/data/`, and
keep it out of version control.

### Cloud upload

Vendo Cloud uploads capability misses when, and only when, both of these hold:

- `VENDO_API_KEY` is set to a non-empty value
- the environment does not trip a kill switch (see below)

The non-empty API key is the host's explicit opt-in, so production runs upload
misses by default once a key is present. Neither the `NODE_ENV` fail-close
(which applies only to the dev-server runtime collector) nor the persisted
`optedOut` flag in `~/.vendo/telemetry.json` gates this stream.

Any of these environment values blocks upload for the current process:

| Variable | Blocks upload when |
| --- | --- |
| `VENDO_TELEMETRY_DISABLED` | equal to `"1"` or `"true"` |
| `DO_NOT_TRACK` | equal to `"1"` or `"true"` |
| `CI` | set to any value other than `""`, `"0"`, or `"false"` |

Uploads are best-effort, batched, and bounded by retry and timeout limits, so
they never replace or delay the local append. When no API key is set, or a
kill switch is tripped, nothing leaves the machine. The local
`.vendo/data/misses.jsonl` file still accumulates so you can inspect misses
locally.

### Downstream use

Uploaded misses feed the Vendo Cloud gap dashboard. The dashboard clusters
them by intent and diffs each cluster against the extracted tool surface named
in the event, so the coverage gaps you see in Cloud match what your local
`.vendo/data/misses.jsonl` records.
