Drop a file. Build on it.

## The picture

Attachments used to ride one message and end with it. A file dropped in chat is
now **saved** — into that user's own files, private to them, still there in next
week's conversation. The agent reads it and answers from it, and can build an
app on top of it.

The message that follows carries only a reference to the file. That is what
keeps a transcript light: a spreadsheet lands once, and the conversation about
it stays a conversation, not a copy of the file repeated on every turn.

Images are the deliberate exception. They still ride the message itself, because
that is how a model sees a picture at all.

## Where files go

Each user gets `/user/files/` inside their own workspace — the same filesystem
the agent works in, scoped to that one person. Nothing is shared between users,
and nothing here belongs to a thread, so a file survives every conversation that
comes after it.

`POST /files` is the door a browser uses:

```http
POST /api/vendo/files?name=sales-2026.csv
Content-Type: text/csv

month,revenue
jan,31000
```

```json
{ "path": "/user/files/sales-2026.csv", "bytes": 24 }
```

The body is the file's own raw bytes under its own media type — there is no
multipart form to assemble, so the name rides the query string, percent-encoded.

<Note>
  **Same name replaces.** Upload `sales-2026.csv` again and the new file *is*
  `sales-2026.csv` — last write wins, no `-v2` suffix, no second copy. This is
  deliberate: re-sending a corrected export is the common case, and a drawer that
  silently accumulated four near-identical spreadsheets would be worse than one
  that keeps the newest.
</Note>

A name is a **file name**, never a path. `nested/report.csv` and `../escape.csv`
are refused rather than quietly rewritten, so nothing can address anything
outside the user's own files.

## From the browser

The client does it in one call — no upload state to manage:

```ts
const saved = await client.files.upload(file);
// { path: "/user/files/sales-2026.csv", bytes: 86104 }
```

The built-in chat surface already does this for you: dropping a file on the
thread, or picking one with the paperclip, uploads it and sends the reference.

## From your own code

`putUserFile` is the same write, called server-side — for pushing a file at a
user without waiting for them to bring it:

```ts
await vendo.putUserFile({
  principal: { kind: "user", subject: user.id },
  name: "statement-2026-08.pdf",
  content: bytes,
});
```

It writes exactly what the chat door writes, so nothing downstream can tell the
two apart. It **delivers nothing and starts no turn** — the file is simply there,
and the user reaches it the next time they chat.

## What the agent does with it

Two tools come with every deployment — no adapter, no key, no configuration:

| Tool | What it does |
| --- | --- |
| `vendo_user_files_list` | What this user has shared, with each file's size and type |
| `vendo_user_files_read` | Reads one of them, by name |

Both are `read` risk and run through the same guard, audit trail and approval
rules as every other tool. Neither takes a path — only a **file name** — so
nothing they are asked for can address anything outside that one user's files.

A long file is read a window at a time (200 lines per call), so a spreadsheet
gets walked rather than truncated. Files that are not text answer with their
type and size and no content: the agent will tell your user it received a PDF
rather than guess at what is inside it.

Because the tools are on the ordinary registry, the listing is also how the
agent finds a file in a **later** conversation. Nothing about last month's
upload is in this conversation's history — the agent looks, finds it, and reads
it.

## Building on a file

Ask for a dashboard of a spreadsheet and the agent builds an app, copying what
it needs — the rows of a table become the app's own saved items.

That copy is a **snapshot, not a live link**. The app does not read the user's
files afterwards, and nothing re-reads them on its behalf.

<Note>
  **Refresh is the agent's job, never a background sync.** Send a newer
  `sales-2026.csv` and the agent recognises it, says the file was replaced, and
  updates what it built from the new contents — on that turn, because the person
  asked. There is no watcher, no polling, and no automatic rebuild anywhere in
  this design. A file sitting in the drawer changes nothing until someone talks
  to the agent about it.
</Note>

<Warning>
  In this release a PDF or an image **lands in the drawer and can be read about,
  but does not reach an app**. Only tabular data is copied into an app. Putting a
  document into an app's own file storage is a follow-up.
</Warning>

## Size

An upload through `POST /files` is capped at **5 MB**. That is a cap on the
*door* — on what a browser may push in one request — and it is enforced there,
so an over-cap upload comes back as a `400` before anything is written.

`putUserFile` is a trusted caller and the door's cap does not apply to it. What
bounds it instead is storage: with no `files:` adapter configured, files are kept
in your store's own blobs, up to 5 MB each. Wire your own bucket to raise that:

```ts
createVendo({
  files: myS3Bucket, // any FilesAdapter: put / get / delete
});
```

That is the same BYO seam every other Vendo capability has — anything
S3-compatible works, and nothing about it requires a Vendo Cloud key. `vendo
doctor` prints where a deployment's uploads land, and the boot block adds a
`files` row when you have wired an adapter of your own.
