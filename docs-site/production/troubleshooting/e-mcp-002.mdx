# E-MCP-002

<Warning>
**what doctor prints** (broken)

MCP authorization-server metadata resolves (404)
</Warning>

Callers can find the door's protected resource, but not the authorization
server that is supposed to issue tokens for it.

`check mcp/authorization-server` · `error_code E-MCP-002` · `doctor exits 1`

## What you're seeing

Doctor's next probe after the protected-resource document, checking whether
the door's authorization server answers with a valid RFC 8414 metadata
document.

## Why

The check runs differently depending on how the door is fronted. In local
mode, doctor fetches
`<origin>/.well-known/oauth-authorization-server<mount>/mcp` directly and
expects an `issuer` string back.

In broker mode (`VENDO_MCP_BROKER_URL` set, or `mcp.remoteAs` configured), the
door names an external authorization server inside its protected-resource
document instead of serving its own. Doctor reads that
`authorization_servers[0]` entry and resolves metadata from the named server.
Two extra failures are possible here: the field can be missing, or it can
name a value that is not a parseable URL, in which case doctor never attempts
a fetch at all.

## The fix

In local mode, this is the same wiring problem as
[E-MCP-001](/production/troubleshooting/e-mcp-001): make sure the
`.well-known` routes are reachable at the origin and the probed URL matches
the real mount.

In broker mode, confirm `VENDO_MCP_BROKER_URL` (or `mcp.remoteAs`) points at a
broker that is actually reachable, and that its own
`/.well-known/oauth-authorization-server` document names itself as `issuer`.
A broker that is down or misconfigured breaks this check even when your own
door is fine.
