Vendo puts an agent inside your product. It works through your own API, signed
in as the person using the app, so it can only do what that person could
already do by clicking. And it answers with screens instead of paragraphs: a
chart, a table, a form they can fill in, rendered in your brand inside your
app.

## What it is not

- Not a chatbot over your docs. It calls your API and changes real data.
- Not a hosted copy of your product. Your server runs the turn, your database
  holds the state.
- Not a rewrite. One package, one route file `vendo init` writes, and one
  provider wrapped around your layout.

## The shape of it

```text
your user ──▶ Vendo surface ──▶ the harness ──▶ GUARD ──▶ your API
 (in your app)   (your brand)   (who thinks)  (policy,     (your data,
      ▲                                        approvals,   your auth,
      └────── generated screen ◀── sandbox ─── audit)       as this user)
```

Nothing reaches your API without passing the guard, which is where a
destructive call stops and waits for someone to approve it. See
[Tools and safety](/concepts/tools-and-safety).

## Which pieces do I need

`createVendo` composes eight slots. Seven of them default. The eighth, `auth`,
is the one you have to answer, and `vendo init` answers it by reading your
`package.json`.

| Slot | What it is | With zero config | When you'd swap it |
| --- | --- | --- | --- |
| `auth` | who the agent acts as on every call | No default. Init detects Auth.js, Clerk, Supabase, or Auth0 and writes the preset. `createVendo` refuses to compose without one. | Your login is homegrown, or an away run needs `actAs`. [Host auth](/deploy/auth) |
| `tools` | your API, as calls the agent can make | Read from `.vendo/tools.json`, which `vendo init` and `vendo sync` extract from your routes, OpenAPI spec, or tRPC router. | The declarations live somewhere a filesystem can't reach, like a Worker. [API tools](/capabilities/api-tools) |
| `skills` | SKILL.md files the agent lists cheaply and opens only when it needs one | Whatever Vendo's own blocks bring, mounted at `/host/skills`. | You want to teach it a procedure of your own. [Handler options](/reference/handler-options) |
| `harness` | who thinks: the loop that runs a turn | `vendo()`, the built-in turn runtime. | You'd rather run a driver on a sandbox machine, or your own loop. [How Vendo works](/concepts/architecture) |
| `models` | which model answers | `VENDO_API_KEY` routes to Vendo's gateway. With no credential at all, every call fails and prints how to fix it. | You want your own provider key, or a different model per seat. [Model credentials](/deploy/model-credentials) |
| `store` | threads, apps, grants, audit | An embedded PGlite database under `.vendo/data`. Nothing to install. | You're deploying somewhere the disk won't survive a release. [Persistence](/deploy/persistence) |
| `files` | workspace file content once it outgrows a row | The store's own blob table, up to 5 MiB. The first write over that fails and names this key. | You want S3, R2, Supabase, or MinIO behind it. [Persistence](/deploy/persistence) |
| `sandbox` | the machine generated apps run server code on | Nothing. Chat and client-rendered screens work. Server-side app code answers "sandbox unavailable". | Your generated apps need to run server code. [Generated UI](/capabilities/generated-ui) |

## What it costs to try

Nothing to provision. The store is an embedded PGlite database inside your
repo, so there is no Postgres to stand up and no container to run.

You do need a model credential. Put an `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`,
or `GOOGLE_GENERATIVE_AI_API_KEY` in `.env.local` and `vendo init` writes the
matching `models:` line into your composition. A key sitting loose in the
environment picks nothing on its own. The line in your config is what selects.

Vendo Cloud is one optional key, `VENDO_API_KEY`. It fills the slots you left
unset: metered inference, a hosted store, sandboxes. An adapter you pass
yourself always beats it, and nothing in these docs requires it.
