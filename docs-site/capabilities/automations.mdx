## How one gets made

The user asks for it in words. There is no separate automations tool and no form to fill in.

```text
"Every weekday at 8am, email me the invoices that went overdue overnight."
```

Vendo builds the app with that trigger attached, and arms it in the same turn. One app can hold several triggers, so a second schedule is added the same way.

## The three triggers

A trigger is one of three shapes. Each carries what to run alongside when to run it.

<CardGroup cols={3}>
  <Card title="Schedule" icon="clock">
    A five-field cron, a plain interval, or a one-shot timestamp.

    `cron` · `every` · `at`
  </Card>
  <Card title="Host event" icon="bolt">
    Your own product event, emitted from the code path that owns it.

    `vendo.emit(...)`
  </Card>
  <Card title="Outside delivery" icon="inbox">
    A signed webhook from a connected service.

    `connector` · `event`
  </Card>
</CardGroup>

```ts trigger shapes
{ kind: "schedule", cron: "0 8 * * 1-5" }
{ kind: "schedule", every: "15m" }
{ kind: "schedule", at: "2026-09-01T09:00:00Z" }
{ kind: "host-event", event: "invoice.paid" }
{ kind: "external", connector: "gmail", event: "message.new" }
```

A schedule carries exactly one of `cron`, `every`, or `at`. Cron is five fields and evaluates in UTC.

<Note>
  A missed window never back-fills. The next fire happens once, from now.
</Note>

## Who fires it

Under a Cloud key, Cloud's scheduler is the firing authority. Your deployment does not run a cron, and the local engine stands down so nothing double-runs.

Host events are different: they fire in your own process, on the code path that emitted them.

```ts
await vendo.emit("invoice.paid", invoice, principal);
```

That runs every armed automation listening for `invoice.paid`, for this user and for the orgs they belong to. It answers with the run ids it started.

<Note>
  A dev server fires its own schedules. Cloud's scheduler cannot reach localhost, so development never waits on it.
</Note>

## Permissions before the first fire

A run happens with nobody there to approve anything, so the permissions are settled when the automation is turned on.

Arming answers with the asks it still needs. Once those are granted, the automation runs as the person who armed it, every time.

Two things stop a trigger on their own: editing what it does, and the sponsor losing access to the app. The run stops before any tool call, and the list carries the reason.

## Watching runs

Every fire writes a run. One hook carries the panel you build around them.

```tsx
const { automations, enable, disable, runs, dryRun, stopRun, rerun } = useAutomations();
```

- `dryRun` shows the plan a fire would follow, without firing it.
- `stopRun` cancels a run that is still going. A run that already finished answers with a conflict.
- `rerun` starts a fresh run of the same automation on the same triggering event. It is the second half of grant-and-retry.
