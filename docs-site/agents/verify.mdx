---
title: "Verify: every doctor error code"
description: "Symptom, cause, and exact fix for every error code vendo doctor can emit. fix_ref URLs from the doctor JSON output anchor into this page."
---

`npx vendo doctor --json` is the install gate. It prints one JSON object; each
check carries a stable `id`, and every failing or warning check carries an
`error_code` from the registry below plus a `fix_ref` URL that anchors into
this page. Exit 0 means no `broken` checks: that is the definition of
installed. Warnings do not block.

The remediation loop: run doctor, open the `fix_ref` for each non-`ok` check,
apply the fix, run doctor again. Repeat until exit 0.

Doctor probes the wire at `http://localhost:3000/api/vendo` by default;
override with `--url <base>` or `VENDO_URL`. In `--json` mode doctor never
starts the dev server itself: start it yourself before running the live
checks.

## Wiring

### E-WIRE-001 {#E-WIRE-001}

**Symptom:** Express server is not wired with createVendo from
`@vendoai/vendo/server`.

**Cause:** Doctor scanned the repo's source files and found none that imports
`@vendoai/vendo/server` and calls `createVendo(`. The composition module is
missing or imports from the wrong specifier.

**Fix:** Run `npx vendo init`; it scaffolds `vendo/server.ts` (or
`server.mjs`) with the composition. If you composed by hand, make sure the
file imports from `@vendoai/vendo/server` and calls `createVendo({...})`.

### E-WIRE-002 {#E-WIRE-002}

**Symptom:** Express client is not wrapped in `<VendoProvider>`.

**Cause:** No source file contains a `<VendoProvider` element. The client half
of the wiring was never pasted.

**Fix:** In the client entry, wrap the app:

```tsx
import { VendoProvider } from "@vendoai/vendo/react";
import type { VendoTheme } from "@vendoai/vendo";
import theme from "<path-to>/.vendo/theme.json";

root.render(
  <VendoProvider baseUrl="/api/vendo" theme={theme as VendoTheme}><App /></VendoProvider>,
);
```

`vendo init` prints this wrap with resolved paths for your repo. The cast
narrows TypeScript's widened JSON-module string literals.

### E-WIRE-003 {#E-WIRE-003}

**Symptom:** Missing `app/api/vendo/[...vendo]/route.ts`.

**Cause:** The Next.js catch-all handler does not exist at
`app/api/vendo/[...vendo]/route.ts` or `src/app/api/vendo/[...vendo]/route.ts`.

**Fix:** Run `npx vendo init`; it scaffolds the route. Do not mount the
handler anywhere else; doctor checks these two paths only.

### E-WIRE-004 {#E-WIRE-004}

**Symptom:** No client entry mounts `<VendoProvider>`.

**Cause:** No `layout.tsx` (or `.jsx`/`.js`) under `app/` or `src/app/` — root
or nested — and no `pages/_app.tsx` (or `.jsx`/`.js`, under `src/` too)
contains a `<VendoProvider` element.

**Fix:** Paste it yourself — init never writes a client file, so this is
always yours, and it is the last line of init's output. Doctor names the same
file init named. Wrap `{children}` in the layout that covers your pages (or
`<Component {...pageProps} />` in `pages/_app.tsx` on a Pages-Router host):

```tsx
import { VendoProvider } from "@vendoai/vendo/react";

<VendoProvider baseUrl="/api/vendo">{children}</VendoProvider>
```

`baseUrl` is where the wire is mounted, path prefix included.

Have host components? Declare the registry in your own `"use client"` file and
mount the provider there: a Server Component layout cannot pass component
references to a client provider (RSC serialization crashes every page with
"Only plain objects can be passed to Client Components").

### E-WIRE-005 {#E-WIRE-005}

**Symptom:** `@vendoai/vendo` (or the `vendoai` alias) is not declared.

**Cause:** Neither package appears in `package.json` dependencies or
devDependencies.

**Fix:** `npm install vendoai` (a thin alias of `@vendoai/vendo`; either name
works and both ship the `vendo` bin).

### E-WIRE-006 {#E-WIRE-006}

**Symptom:** No visible agent surface is mounted. Everything else can be green
and a user opening the app still sees nothing — `<VendoProvider>` is a context
provider that renders no UI of its own.

**Cause:** Doctor scanned the repo's source files and found none that mounts a
visible surface. The full marker list: `<VendoOverlay`, `<VendoThread`,
`<VendoTrigger`, `<VendoPalette`, `<VendoSlot`, the BYO embeds
(`<VendoToolResult`, `<VendoAppEmbed`, `<VendoApprovalEmbed`), and the
surface-driving hooks (`useVendoOverlay(`, `useVendoThread(`, `useSlotApp(`).

**Fix:** Mount `<VendoOverlay />` (the launcher pill + panel) inside the
provider:

```tsx
import { VendoOverlay } from "@vendoai/vendo/react";

// anywhere inside <VendoProvider>:
<VendoOverlay />
```

BYO-agent hosts that render tool outputs through `<VendoToolResult>` in their
own chat UI already pass this check.

## Config files

### E-WIRE-007 {#E-WIRE-007}

**Symptom:** Doctor found no `createVendo` server wiring in a host it cannot
pattern-match to Next.js or Express (a Cloudflare Worker, Bun server, Hono
app, ...).

**Cause:** No source file imports `createVendo` from `@vendoai/vendo/server`
(or nothing mounts its handler), so there is no Vendo wire for the runtime to
serve.

**Fix:** Import `createVendo` and route your runtime's request entry through
`vendo.handler(request)` — construct lazily (first request), not at module
scope, on edge runtimes.

### E-WIRE-008 {#E-WIRE-008}

**Symptom:** Doctor found no `<VendoProvider>` in an unknown-framework host's
source (warning, not failure).

**Cause:** The `@vendoai/ui` hooks and embeds need the `<VendoProvider>`
context provider; a host that renders them without it gets runtime errors.

**Fix:** Wrap the client app in `<VendoProvider>`. Ignore this warning if the
host drives a fully custom surface without `@vendoai/ui`.

### E-WIRE-009 {#E-WIRE-009}

**Symptom:** The host has live `"use server"` actions, but doctor found them
missing from `app/api/vendo/[...vendo]/vendo-actions.ts`, or found a `route.ts`
that never passes `serverActions` **inside** its `createVendo({ … })` call.
Everything else can be green: the failure only shows up when a user's turn calls
one of those tools, and it fails closed — no work performed, no error the user
can act on.

**Cause:** `vendo init` generates the registration map and the route the first
time it runs, and it only ever *creates* — a file you already have is never
rewritten. Actions added after that first run therefore do not register
themselves. The commonest shape is a half-applied paste: the
`import { serverActions } …` line landed but the `serverActions,` property never
went into the call. An import alone is not wiring.

**Fix:** Run `npx vendo init` again. It prints the exact paste for each file it
will not touch — the import line plus `serverActions,` inside
`createVendo({ … })`, and the missing map entries (only the missing ones, with
aliases that continue your file's own numbering). Apply them and re-run doctor.

**Not reported:** actions you disabled in `.vendo/overrides.json` (or that a
judgment disabled) — the runtime never dispatches those, so registering them
buys nothing. Nor a route that passes a `serverActions` map it composes itself;
init leaves that shape alone and doctor has no generated map to grade.

### E-WIRE-010 {#E-WIRE-010}

**Symptom (warning):** The host still names `<VendoRoot>`, or still carries the
`vendo/vendo-root.tsx` wrapper older versions of `vendo init` generated.

**Cause:** `VendoRoot` was removed; `VendoProvider` is the only provider, and it
takes the wire mount as `baseUrl`.

**Fix:** Three lines. Change the import to
`import { VendoProvider } from "@vendoai/vendo/react"`, rename the tag to
`<VendoProvider>`, and add `baseUrl="/api/vendo"` (include your deployment's
path prefix if it has one). The props are otherwise identical. A generated
`vendo/vendo-root.tsx` is YOUR file now — edit it in place or fold it into your
layout.

### E-CFG-001 {#E-CFG-001}

**Symptom:** A required `.vendo/` file is missing; the message names it, one
of `tools.json`, `overrides.json`, `policy.json`, `brief.md`, `theme.json`.

**Cause:** `vendo init` was never run in this directory, or the file was
deleted.

**Fix:** Run `npx vendo init`; it recreates missing `.vendo/` files and never
overwrites existing ones. A missing `tools.json` alone can also be regenerated
with `npx vendo sync`.

### E-CFG-002 {#E-CFG-002}

**Symptom (warning):** `.vendo/data/.gitignore` is missing.

**Cause:** The gitignore that keeps the local PGlite store out of version
control was deleted, so `.vendo/data/` contents could get committed.

**Fix:** Run `npx vendo init`, or create `.vendo/data/.gitignore` containing:

```text
*
!.gitignore
```

### E-CFG-003 {#E-CFG-003}

**Symptom:** The OpenAPI spec's relative `servers[0].url` and `VENDO_BASE_URL`'s
path prefix disagree — every page renders and every host tool call 404s.

**Fix:** Set `VENDO_BASE_URL` to the app's full public URL including the spec's
server mount (`https://site.com/maple`), or drop the relative server from the
spec if the app is not mounted under a prefix.

## Host dependencies

### E-DEP-001 {#E-DEP-001}

**Symptom:** The installed `ai` package is major version 7 or newer; the
message names the exact version found.

**Cause:** `@vendoai/vendo` drives the host's `ai` package with AI SDK v6
calls (peer range `ai >=6 <7`), but npm installs the peer conflict without
failing. Every static check passes on such a host — and then every internal
Vendo turn throws `AI_InvalidPromptError`, because ai@7 removed system-role
messages from the messages array.

**Fix:** Downgrade to the supported majors:

```bash
npm install ai@^6 @ai-sdk/anthropic@^3 @ai-sdk/react@^3
```

ai@7 support is tracked in
[runvendo/vendo#478](https://github.com/runvendo/vendo/issues/478).

### E-DEP-002 {#E-DEP-002}

**Symptom:** The running wire's `/status` reports a different `@vendoai/vendo`
version than the CLI running doctor; the message names both versions.

**Cause:** A split-brain install. A direct `@vendoai/vendo` dependency pinned
to an older range wins over the `vendoai` umbrella's for the app import, so
`npm install vendoai@latest` upgrades the CLI while the app silently keeps
serving the old runtime. A dev server started before an upgrade shows the
same skew until restarted.

**Fix:** Align the runtime with the CLI, then restart the dev server:

```bash
npm install @vendoai/vendo@<cli-version>
```

or remove the direct `@vendoai/vendo` dependency from `package.json` (the
`vendoai` umbrella provides it) and reinstall. Re-run doctor after the dev
server restarts.

### E-DEP-003 {#E-DEP-003}

**Symptom:** The installed `zod` is older than 3.25; the message names the
exact version found. Without the fix, `next build` (or any bundling build)
fails with `Package path ./v3 is not exported from package zod` — a
module-not-found deep inside `ai`.

**Cause:** The AI SDK (`ai@6`) imports the `zod/v3` and `zod/v4` subpaths,
which first ship in zod 3.25. When the app pins an older zod (a common
`^3.2x` range resolving below 3.25), the app's own pin wins the installed
tree, and the build breaks the moment Vendo's wiring pulls `ai` into the
bundle. `vendo init` detects this and offers the bump; this check catches
hosts that declined or predate that detection.

**Fix:** Bump zod within v3 (3.25 satisfies the common `^3.2x` ranges and
keeps zod 3 semantics):

```bash
npm install zod@^3.25.0
```

Hosts already on zod 4 are unaffected (zod 4 exposes both subpaths).

## Ejected UI

### E-UI-001 {#E-UI-001}

**Symptom (warning):** An ejected surface came from an older `@vendoai/ui`
than the one installed.

**Cause:** You ejected a chrome surface, then upgraded `@vendoai/ui`. The
ejected pixels are your code, so nothing is broken; only newer presentation
is missed.

**Fix:** Review the [release notes](https://github.com/runvendo/vendo/releases)
and run `npx vendo eject <surface> --force` if you want the new presentation.
Leaving it is also valid; this never blocks doctor.

## Dev server

### E-DEV-001 {#E-DEV-001}

**Symptom (warning):** The dev server could not be started for the probe.

**Cause:** Interactive doctor offered to start the dev server (`run dev` via
your package manager) and `/status` never answered within the startup window.

**Fix:** Start the dev server yourself (for example `npm run dev`), wait until
it serves, and re-run `vendo doctor`. If the app listens on a non-default port
or mount, pass `--url <base>` or set `VENDO_URL`. Note: `--json` runs never
attempt the start; agents own the dev server.

## Live composition

### E-LIVE-001 {#E-LIVE-001}

**Symptom:** `/status` returned an invalid composition response.

**Cause:** Something answered at `<base>/status` but not with the Vendo status
shape (`posture`, `version`, `blocks`). Usually another handler owns the path,
the mount is wrong, or the base URL points at the wrong app.

**Fix:** Confirm the Vendo handler is mounted at the probed base (Next:
`app/api/vendo/[...vendo]/route.ts`; Express: `app.use("/api/vendo",
mountVendo())`, where `mountVendo` is the adapter init generated into your own
`vendo/server.ts` — no package exports it) and that `--url`/`VENDO_URL` points
at it.

### E-LIVE-002 {#E-LIVE-002}

**Symptom:** `/status` is unreachable.

**Cause:** Nothing is listening at the probed base: the dev server is not
running, it runs on a different port than the probe target, or `--url` was
given the site root instead of the wire base.

**Fix:** Start the dev server and re-run doctor. `--url` expects the WIRE
BASE — your app origin plus the mount path (for example
`http://localhost:3000/api/vendo`), not the bare origin. The default probe
base is `http://localhost:3000/api/vendo`; override with `--url <base>` or
`VENDO_URL`. All live checks (auth probes, model turn) depend on this one.

### E-LIVE-003 {#E-LIVE-003}

**Symptom:** `/status` returned an invalid execution venue.

**Cause:** `blocks.sandbox` in the status response is not one of the known
venues (`e2b`, `cloud`, `custom`), `false`, or absent. The status
route is patched or the composition is corrupted.

**Fix:** Remove any custom `/status` handling and upgrade `@vendoai/vendo` so
the stock status route answers.

### E-LIVE-004 {#E-LIVE-004}

**Symptom (warning):** No execution venue is configured.

**Cause:** The composition has no sandbox adapter, so user apps that need a
server (anything beyond tree-only rendering) return sandbox-unavailable.
Tree-only apps still work.

**Fix:** One of: install the `e2b` package and set `E2B_API_KEY`; set
`VENDO_API_KEY` for the managed Cloud sandbox; or pass `sandbox:` to
`createVendo`. Ask your human which venue they want; this needs an account or
key.

### E-LIVE-005 {#E-LIVE-005}

**Symptom (warning):** The host `/status` does not report an execution venue.

**Cause:** Version skew: the installed `@vendoai/vendo` predates the
`blocks.sandbox` field, so the venue check cannot run.

**Fix:** Upgrade: `npm install vendoai@latest`, restart the dev server, re-run
doctor.

### E-LIVE-006 {#E-LIVE-006}

**Symptom:** The app's root page returns a 5xx while the wire answers — the
site is down for actual users even though every API-level check passes.

**Cause:** Doctor GETs the app origin's root page after `/status` succeeds.
The most common cause after a fresh install is the component registry imported
in a Server Component layout and passed to the client provider: React refuses
to serialize component references across the boundary and every page 500s.

**Fix:** Read the dev server log for the real stack. For the registry case,
mount the generated `vendo/vendo-root.tsx` wrapper in the layout instead of
importing the registry there (see [E-WIRE-004](#E-WIRE-004)); re-run
`npx vendo init` to generate the wrapper if it is missing.

### E-LIVE-007 {#E-LIVE-007}

**Symptom:** `/status` reports the e2b execution venue, but `E2B_API_KEY` is
not set for this project or the `e2b` package does not resolve from it.

**Cause:** The running wire selected e2b as the sandbox venue that it cannot
actually use — typically an `E2B_API_KEY` inherited from the shell without the
`e2b` package installed. Server-app builds die in the unusable venue instead
of riding the managed Cloud sandbox.

**Fix:** To use e2b, install the `e2b` package and set `E2B_API_KEY` in the
project env. To use the managed Cloud sandbox instead, remove `E2B_API_KEY`
from the server env and keep `VENDO_API_KEY` set. Restart the dev server and
re-run `vendo doctor`.

## Auth probes

### E-AUTH-001 {#E-AUTH-001}

**Symptom:** Present credentials did not reach the host API.

**Cause:** Doctor POSTed `<base>/doctor/present` with seeded cookie and
authorization headers, and they did not come back through the wire's
same-origin fetch. The wire does not trust the origin it is being probed on,
so it strips credentials instead of forwarding them.

**Fix:** Set `VENDO_BASE_URL` to the running host origin (for example
`VENDO_BASE_URL=http://localhost:3000` in `.env.local`), restart the dev
server, and re-run doctor.

### E-AUTH-002 {#E-AUTH-002}

**Symptom:** The present credential probe is unreachable.

**Cause:** `/status` answered but `<base>/doctor/present` threw: the dev
server died mid-run or a proxy blocks the doctor routes.

**Fix:** Restart the dev server, verify `VENDO_BASE_URL`, and re-run doctor.

### E-AUTH-003 {#E-AUTH-003}

**Symptom:** The present credential probe cannot run while the dev server is
down.

**Cause:** Follows from a failed `/status` round-trip; see
[E-LIVE-002](#E-LIVE-002).

**Fix:** Start the dev server at the probed base and re-run doctor; this check
runs once `/status` answers.

### E-AUTH-004 {#E-AUTH-004}

**Symptom:** actAs mint + host verification failed.

**Cause:** The composition minted an away credential but the host did not
verify it. The verifier middleware is missing, or the secret the preset signs
with differs from the one the host verifies with.

**Fix:** Check `createVendo({ auth })` (or the hand-wired `actAs`), its
verifier middleware on the host API, and the host principal resolver. For
Clerk/Auth0, `VENDO_AWAY_TOKEN_SECRET` must be the same value on both sides.
See [Host auth](/agents/host-auth).

### E-AUTH-005 {#E-AUTH-005}

**Symptom:** The actAs probe is unreachable.

**Cause:** `/status` answered but `<base>/doctor/act-as` threw.

**Fix:** Restart the dev server, check `createVendo({ actAs })` (or the `auth`
preset), and re-run doctor.

### E-AUTH-006 {#E-AUTH-006}

**Symptom:** The actAs probe cannot run while the dev server is down.

**Cause:** Follows from a failed `/status` round-trip; see
[E-LIVE-002](#E-LIVE-002).

**Fix:** Start the dev server at the probed base and re-run doctor.

### E-AUTH-007 {#E-AUTH-007}

**Symptom (warning):** actAs is not configured.

**Cause:** The composition has neither an `auth` preset nor an `actAs` seam,
so the agent cannot act through the host API while the user is away. Present
(user-in-the-room) calls still work.

**Fix:** Wire an auth preset (`auth: authJs()` and friends fill `actAs`) or
pass `createVendo({ actAs })` before enabling away host actions. Acceptable to
leave for a present-only install; this never blocks doctor.

## MCP door

These checks run only when the composition reports `blocks.mcp: true`.

### E-MCP-001 {#E-MCP-001}

**Symptom:** MCP protected-resource metadata did not resolve.

**Cause:** `GET <origin>/.well-known/oauth-protected-resource<mount>/mcp` did
not return a JSON object with a `resource` string. The metadata is
path-inserted (RFC 9728): a door at `/api/vendo/mcp` serves
`/.well-known/oauth-protected-resource/api/vendo/mcp`.

**Fix:** Make sure the composition passes `mcp: true` with a working
`auth`/`oauth` seam, the `.well-known` route is reachable at the origin (not
swallowed by a proxy or middleware), and the probed `--url` matches the real
mount.

### E-MCP-002 {#E-MCP-002}

**Symptom:** MCP authorization-server metadata did not resolve.

**Cause:** `GET <origin>/.well-known/oauth-authorization-server<mount>/mcp`
did not return a JSON object with an `issuer` string.

**Fix:** Same as [E-MCP-001](#E-MCP-001): the two documents are served by the
same door wiring; check the oauth adapter configuration.

### E-MCP-003 {#E-MCP-003}

**Symptom:** The MCP server card did not parse.

**Cause:** `GET <origin>/.well-known/mcp/server-card.json` did not return an
object with a `name` string and a `transports` array.

**Fix:** Check that the door's well-known routes are mounted at the origin and
nothing rewrites the card response.

### E-MCP-004 {#E-MCP-004}

**Symptom:** `server.json` does not meet MCP registry discovery requirements;
the message lists the exact validation errors.

**Cause:** The repo has a `server.json` (the official MCP registry artifact)
that fails schema validation.

**Fix:** Regenerate it: `npx vendo mcp server-json --domain <domain> --url
<public-mcp-url> --force`, or fix the listed fields by hand.

### E-MCP-005 {#E-MCP-005}

**Symptom:** The `server.json` remote does not match the live MCP door.

**Cause:** The remote URL declared in `server.json` differs from the door
doctor just probed; the file predates a URL or mount change.

**Fix:** Regenerate `server.json` with the current public door URL: `npx vendo
mcp server-json --domain <domain> --url <public-mcp-url> --force`.

### E-MCP-006 {#E-MCP-006}

**Symptom:** `server.json` is invalid JSON.

**Cause:** The file does not parse.

**Fix:** Regenerate it with `npx vendo mcp server-json` (see
[E-MCP-004](#E-MCP-004)) or repair the syntax.

### E-MCP-007 {#E-MCP-007}

**Symptom:** The local MCP registry auth challenge is malformed.

**Cause:** `public/.well-known/mcp-registry-auth` exists but does not start
with `v=MCPv1`.

**Fix:** Regenerate the domain-verification material: `npx vendo mcp
verify-domain --domain <domain> --key-out <path> --write-well-known public`.

### E-MCP-008 {#E-MCP-008}

**Symptom:** The live MCP registry auth challenge is malformed.

**Cause:** `GET <origin>/.well-known/mcp-registry-auth` serves content that
does not start with `v=MCPv1`, usually a stale or hand-edited deployed copy.

**Fix:** Redeploy the file generated by `npx vendo mcp verify-domain` (see
[E-MCP-007](#E-MCP-007)); DNS verification is an alternative to serving it
over HTTP.

### E-MCP-009 {#E-MCP-009}

**Symptom:** The MCP door is wired but `VENDO_BASE_URL` is not set.

**Cause:** The composition passes `mcp` to `createVendo`, and neither
`VENDO_BASE_URL` nor `mcp: { baseUrl }` names the deployment's public origin.
The door's discovery documents, its issuer, its resource identifiers and its
RFC 8707 audience binding all derive from that one value, so the door
advertises whatever origin the request happened to carry. Nothing looks wrong
locally; it surfaces later, in someone else's terminal, as "Claude can't find
my server".

**Fix:** Set `VENDO_BASE_URL` to the deployment's full public URL — path prefix
included — where you deploy, or pass `mcp: { baseUrl }` in the composition.

## Machine schedules

### E-SCHED-001 {#E-SCHED-001}

**Symptom (warning):** Apps declare `vendo.json` schedules but no schedule
caller is configured.

**Cause:** At least one machine-bearing app's `vendo.json` declares a
schedule, but `VENDO_TICK_SECRET` is not set, so nothing can hit the
authenticated `POST /api/vendo/tick` surface and the schedules never fire.

**Fix:** Set `VENDO_TICK_SECRET` to a random secret in the server environment,
then point any external cron — Vercel cron, a GitHub Actions schedule, or
crontab — at `POST <base>/tick` with the header
`Authorization: Bearer $VENDO_TICK_SECRET`. Every hit fires due schedules
exactly once per cron window; a double-hit is a safe no-op.

## Live model turn

### E-TURN-001 {#E-TURN-001}

**Symptom:** The live model turn did not answer; the message names the
credential used and the error.

**Cause:** Doctor POSTed one real turn to `<base>/threads` and no reply text
arrived: no usable model credential, a provider error, or a timeout (90s).

**Fix:** Check the credential the message names. With no key set, add
`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, or `GOOGLE_GENERATIVE_AI_API_KEY` to
`.env.local` (with the matching `@ai-sdk/*` provider installed), or use a
free Vendo Cloud dev key: run `vendo login` (your human approves a code in
the browser; non-TTY runs print the URL + code) — the minted key lands in
`.env.local` (ask your human first). Then restart the dev server and check
its logs for the turn error.

### E-TURN-002 {#E-TURN-002}

**Symptom:** The live model turn cannot run while the dev server is down.

**Cause:** Follows from a failed `/status` round-trip; see
[E-LIVE-002](#E-LIVE-002).

**Fix:** Start the dev server at the probed base and re-run doctor.

## Vendo Cloud

### E-CLOUD-001 {#E-CLOUD-001}

**Symptom (warning):** `VENDO_API_KEY` is set but not usable.

**Cause:** The key fails the local shape check (expected `vnd_` + 40 hex
characters). Doctor never validates keys against a server; a well-formed but
revoked key surfaces on the first real service call instead.

**Fix:** Re-copy the key from the Vendo Cloud console, or mint a fresh one:
run `vendo login` (your human approves a code in the browser) — the minted
key lands in `.env.local` (ask your human first). Unsetting `VENDO_API_KEY`
also clears the warning; Cloud is optional.


### E-TOOLS-001 {#E-TOOLS-001}

**Symptom:** Every extracted host tool is disabled or excluded — the embedded
agent cannot call a single host API.

**Cause:** All entries in `.vendo/tools.json` are disabled, either statically
or by `.vendo/overrides.json` (including extraction's audience exclusions:
operator/internal endpoints are excluded by default).

**Fix:** Review `.vendo/overrides.json`; re-enable the end-user surface with
`"disabled": false` on tools users should reach, or re-run `vendo init`
extraction if the surface classification looks wrong.

### E-TOOLS-002 {#E-TOOLS-002}

**Symptom:** `.vendo/tools.json` carries zero tools (warning, not failure).

**Cause:** Extraction found no end-user API surface, or every proposed tool
was removed by hand.

**Fix:** Re-run `vendo init` extraction. Connector-only deployments (the
agent works purely through connected third-party tools) can ignore this
warning.

### E-TOOLS-003 {#E-TOOLS-003}

**Symptom:** `catalog: N/M tools ungraded` (warning, not failure).

**Cause:** Nobody has graded those tools. Extraction only asserts protocol
facts — an HTTP `DELETE` is destructive, a declared tRPC mutation is at
least a write — and never guesses a grade from a tool's name. Everything
else is `ungraded` until the AI judge or a human says otherwise, and the
guard asks the user before every ungraded call rather than running it.

**Fix:** Run `vendo sync` with a model key so the judgment pass grades the
catalog against the real handler source. Without a key, grade the tools you
care about by hand in `.vendo/overrides.json`:

```json
{ "tools": { "host_invoices_list": { "risk": "read" } } }
```

Leaving them ungraded is safe — it just means an approval prompt per call.

### E-TOOLS-004 {#E-TOOLS-004}

**Symptom:** `catalog: inputs N/M · outputs N/M — blind: …` (warning, not failure).

**Cause:** Those tools declare no request schema, no response schema, or
neither. Nothing is broken — a blind tool still runs, permissively — but the
agent is working without the contract: it cannot know a blind tool's arguments
(and must not assume it takes none), and it has to pass a blind tool's whole
output through instead of binding to the two fields a screen needs.

Where the schemas come from, best first: your own contract (an OpenAPI
response schema, a tRPC `.output()`, a typed server action),
then the AI judge reading the handler source, then nothing.

**Fix:** Declare the shapes in the contract you already publish — that is the
only rung that survives a refactor. For handlers with no contract to declare
(a bare Next route), run `vendo sync` with a model key so the judgment pass
reads the handler and fills the blind slots; it never overwrites a slot your
contract already filled.

Leaving them blind is safe. It just costs the agent precision.
